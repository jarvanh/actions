## 四、根因链

```
目标后端 wopan176Crypt 对加密后的长路径拒绝写入
   └→ OpenList 包装成 HTTP 405（内部 8005）返回给 rclone
        └→ 批量 rclone sync 每个文件都 405（1050/1051）
             └→ 引擎判定为 8005 登录失败 → 刷新 token → 整批重跑 ×3
                  └→ 405 是确定性的，重跑不会有第二种结果，烧掉 ~3.5h
                       └→ 只剩 ~50min 给修复管线 → 73 个文件
```

佐证（同一批文件、同一后端）：

- 原目录 `路人女主/已解压/(C88) [1000000000 (Billion)] 恵の愛…[中国翻訳]` → **不可写**
- 折叠成短哈希目录 `4dd7e9d7` 后 → **可写**，修复方法 1/2 均成功
- token 刷新成功后重试，第一个文件立刻又是 405 → **不是 token 过期**

即：短哈希目录兜底本身是有效的，问题在于它只在**修复阶段**才触发，
批量同步阶段对整目录反复试原路径，把这轮预算烧光了。

### 修掉的两个 bug

1. **收尾 step 掩盖真实失败**：rclone-install 挂掉后「加载同步函数库」被 skip，
   /tmp/load_all.sh 不存在，收尾 step `source` 报 No such file 再补一个 exit 1，
   把真正的失败原因压在下面（run 34685067684 已发生）。
2. **基础设施失败仍接力**：同一 run 在 install 已失败的情况下，自续触发照常
   dispatch 下一轮 → "失败 → 接力 → 再失败"的空转循环。
   现在两者都要求 `OL_ENV_READY=1`（由「加载同步函数库」step 成功时写入 GITHUB_ENV）。

### 目录级批量折叠（快路径，本轮的核心改动）

`file_fix_pipeline.sh` 新增 `_sync_bulk_hash_dir_fold`，挂在逐文件修复循环**之前**：
缺失文件按目录分组 → 原目录探明不可写 → 整组一次 `rclone sync` 到短哈希目录 →
按目标端实际落盘清单逐条补 marker。

- 复用既有 `_fix_probe_dir_writable` / `_hash_dir_rel_for`，marker 结构与逐文件修复
  **完全一致**（method_id=`copyto_original`、method 文本含"短哈希目录 <hash>"），
  `restore_info.jq` 的 hash_dir 分支照常消费，还原链路零改动
- 不复用 `_fix_switch_to_hash_dir`（它切换后会再探一次可写性，可能触发容器重启
  ~80s，本轮预算仅 3 次）；改用"sync 完按落盘清单校验"，零落盘即退回逐文件修复
- 只对**已探明原目录不可写**的目录动手；时间预算到点即停；后端熔断即停
- 开关 `OPENLIST_BULK_HASH_FOLD`，门槛 `OPENLIST_BULK_FOLD_MIN_FILES`(2) /
  `OPENLIST_BULK_FOLD_MAX_DIRS`(**40**)
- **折叠成功即清除后端熔断**：`_BACKEND_DEAD` 阈值 3（连续 3 个目录不可写）会把
  "43 个长路径目录全都 405"误判成"后端故障"并在第 3 个目录停摆。落盘成功就证明
  后端可写，据此清 `_BACKEND_DEAD` / `_BACKEND_DIR_FAIL_STREAK`
- 记账走**关联数组查表**（落盘清单 `_landed_set`、源端尺寸 `_size_of`），不逐文件
  `grep`/`jq` —— 单目录 1051 个文件时，逐文件起进程光启动开销就是几十秒
- 测试 `tests/test_bulk_hash_fold.sh`（26 项，含零落盘不误记、子目录不串组、
  原目录可写不折叠、预算/熔断即停、不递归搬运、批量规模、预算预留）
- 调用点放在 `OPENLIST_MISSING_FIX_MAX` 截断**之前**: 折叠是批量通道，一轮能解决
  上千个；截断到 200 再折叠等于把快路径也按 200 封顶，剩下的全推给 30s/个的慢路径

## 七、9.9 TB 里有约三分之二是副本（此前没注意到的构成）

`sync_trend.sh:50-57` 确认口径: `remaining_bytes` = `PREVIEW_PENDING_MAP` **各同步对
bytes 之和**，而 `PREVIEW_PENDING_MAP` 的 key 是 `任务名|目标路径` —— **每个同步对
单独计一遍，副本不合并**。

注册表里 16 个同步对 = 6 个源端目录 × 2~3 个目标后端:

| 源端 | 目标后端副本 |
|---|---|
| `onedrive:0` / `onedrive:1` | wopan176Crypt + baidupanCrypt + wopan175（**3 份**）|
| `onedrive:2`~`onedrive:5` | wopan176Crypt + wopan175（**2 份**）|
| `onedrive:backup` | aliyundriveCrypt + wopan176Crypt |

实测源端规模: `onedrive:0` = 281 GiB / 2636 个文件，`onedrive:2` = 925 GiB。
按此量级，去重后的真实待传约 **3~4 TB**，9.9 TB 里约 **2/3 是第二、第三份副本**。

含义:

- 「同步完 9.9 TB」≠「保住 3~4 TB 的数据」——多副本是灾备冗余，值得做，但它把
  工期乘以了 2~3。
- **如果目标是"先有个完整副本"**: 把 baidupanCrypt / wopan175 两列暂时注释掉
  （注册表就在 `task_engine.sh:33-61`，改一行），工期立刻降为 1/2~1/3，
  等主副本（wopan176Crypt）跑完再逐份补。
- 反过来，如果三个副本都必须同时在跑，那 9.9 TB 是刚性的，只能靠提速解决。

## 八、关于 9.9 TB 这个量级本身

即使 405 完全修好，按实测批量速率 2-3 MiB/s、每轮 5.5h、2 轮/天计算，
9.9 TB 仍需约 **83 天**，且要求源端停止增长。GitHub Actions 6h runner
不是为这个量级设计的搬运通道——建议同时评估：把存量迁移放到一台常驻机器上
跑一次全量，Actions 只负责增量。
