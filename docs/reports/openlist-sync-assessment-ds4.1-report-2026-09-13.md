## 2. 根因：目标后端全路径拒写

日志里的 405 是 `unchunked simple update failed: Method Not Allowed`，来自 `openlist:wopan176Crypt`。可以排除"路径太长"这个既有假设：

1. **与文件名长度无关**：失败的 `C_1108_014.jpg`，原名 14 字节、密文名 22 字节，远低于日志自报的后端上限（"后端已接受最长密文名 100 字节"），照样 405。
2. **与目录名长度无关**：`_sync_bulk_hash_dir_fold` 把整个目录折叠成 8 字符短哈希目录（`cb4f0d57` / `f22c8c73`），`rclone sync` 报 `39.jpg: Copied (new)`、21.76 MiB / 100% 传完，**落盘校验为 0**。
3. **与并发无关**：`OPENLIST_TRANSFERS=1`（串行）。
4. **容器日志里有 8005**：`_has_wopan_login_failure` 命中并触发"刷新 token 并重试 1/1"，刷新后第一个文件立刻又是 405。

即：`openlist:wopan176Crypt` 在 2026-09-12 12:35 之后从"长路径拒写"退化为**全路径拒写**（原路径显式 405、短哈希路径静默假成功）。`docs/openlist-sync-health-2026-09-12.md` 里"短哈希目录可写"的结论已不成立。

> 这一条是**运维层面的故障**，不是代码能修的。下面所有代码改动都只能止损；不确认 wopan176 账号（配额 / 限流 / 封禁 / token）状态，工期推算都没有意义。

## 4. 代码层面的缺陷（按实际损失排序）

### 缺陷 1：逐文件修复循环没有后端熔断早退 —— 单轮白烧 119 分钟

- 位置：`file_fix_pipeline.sh:754` 的 `while IFS= read -r failed_line` 循环。
- 循环内只有两个退出条件：时间预算（`:762-767`）和"错误签名熔断"（`:837-860`）。
- 但后端一旦熔断，`try_fix_failed_file` 会在产生任何 `Failed to copyto` 之前就短路（日志原文：`🔀 原目录不可写（后端熔断）→ 跳过原目录的 4 种方法` / `⏭ 文件位于目标端根目录，无目录可换`），于是 `_sig` 恒为空、`_cb_consec` 每次被重置（`:856-859`）——**签名熔断器在熔断态下永远不可能触发**。
- 实测：`08:00:09 → 09:08:53` 439 次 + `09:41:08 → 10:32:22` 89 次 = **528 次尝试、119 分钟、0 成功**，每个文件约 13.5 s 的纯开销（`rclone size` 源端 + mkdir API + 建短哈希目录 + marker 读取）。
- 注：项目长期记忆里写着"逐文件修复循环 / 子目录循环已补 `_BACKEND_DEAD` 读取点"，**代码里不存在**（全库 `_BACKEND_DEAD` 读取点只有 3 处：`file_fix.sh:753`、`file_fix_pipeline.sh:385`、`sync_engine.sh:312`）。

**修法**：在 `:762` 的时间预算检查旁并列一条：

```bash
local _fix_be_root; _fix_be_root=$(_fix_backend_root_of "$dest_path")
if [ "${_BACKEND_DEAD[$_fix_be_root]:-0}" = "1" ]; then
  echo "🛑 后端 ${_fix_be_root} 本轮已熔断，跳过剩余 $((_cb_total - _cb_done)) 个文件" | tee -a "$LOG_FILENAME"
  SYNC_BACKEND_DEAD=1
  break
fi
```

### 缺陷 2：后端写探针写的是挂载根，认证不了真实数据路径

- 位置：`openlist_driver.sh:380-434`，核心一行 `:398 local probe_dst="${root}/${probe_name}"`。
- 三轮全部报 `💉 后端写探针: openlist:wopan176Crypt` / `✅ 后端可写`，而**同一轮的第一个真实写入就 405**：
  - `05:57:44` 探针判可写；
  - `05:59:13` 第一个真实文件 `img000.jpg` → `405 Method Not Allowed`（相隔 89 秒）。
- 探针写在**挂载根**，真实数据全部落在 `openlist:wopan176Crypt/2/1024j/...` 这类子路径下——探针从未覆盖真实写入路径。
- 另外 `:409-412` 的"读回确认"只是一次 `rclone lsf`，没有刷新 OpenList 缓存、也没有重启容器；缓存里的列表同样能满足这个检查，所以它连"PUT 假成功"也未必拦得住（该函数的注释声称拦得住）。

**修法**：探针目标改为真实同步对所在子路径（如 `${dest_path}` 自身或其一级子目录），并在读回前刷新缓存（`/api/fs/refresh`）或复用 truth-check 的重启口径。

**收益**：探针若判死，本轮 330 分钟**全部**省下，而不是烧 119 分钟才发现。

### 缺陷 3：「后端写入全拒」检测用 rclone 的 Copied 行数当判据，恒不触发

- 位置：`task_engine.sh:1130`

```bash
if [ "$missing_n" -ge 3 ] && [ "$retry_copied" -eq 0 ] && [ "$touched_n" -gt 0 ] && [ "$missing_n" -ge "$touched_n" ]; then
  BATCH_BACKEND_DEAD=1
```

- 判据要求"串行重试 0 成功"，而假成功的特征恰恰是 **rclone 报成功**。实测该轮：`批次 1 巩固: 串行重试完成，重传 1037/1037` → `retry_copied=1037` → 判据恒假 → 熔断不触发 → 继续启动批次 2/3。
- 真正的判据就在 30 行之后：`:1147` 用"重启容器后真值 diff"算出 `stubborn`，实测 `1037 个顽固缺失` = 全部触碰文件。**这个信号没被用于熔断。**
- 同一轮日志里 `grep -c "后端写入全拒"` = **0**。

**修法**：把判定下移到 `stubborn_n` 算出之后，判据改为 `stubborn_n >= touched_n && touched_n >= 3`（可选再加"重传 Copied 数与顽固数一致"）。

### 缺陷 4：`SYNC_BACKEND_DEAD` 实际永不置位 → 轮转游标被一个死后端钉住

`SYNC_BACKEND_DEAD` 只有三处置位：

| 位置 | 条件 | 实际 |
|---|---|---|
| `sync_engine.sh:152` | 入口预检写探针判死 | 缺陷 2 → 恒假 |
| `sync_engine.sh:269` | 二次预检写探针判死 | 缺陷 2 → 恒假 |
| `sync_engine.sh:312` | `_BACKEND_DEAD` 置位（修复阶段暴露的后端故障） | **只有正常跑完才执行到**；330 min 超时把 step 杀掉时到不了 |

而消费点 `task_engine.sh:200-218` 只有在 `_run_registry_entry` 正常返回后才会评估。结果：

- `onedrive:/logs/sync_state/task_rotation.json` 当前为 `{"cursor": 8, "attempts": 6}` → 游标钉在 `SYNC_TASK_REGISTRY[8]` = `task2`（`openlist:wopan176Crypt/2`），已连续尝试 6 次。
- 唯一的脱身路径是 `:213` 的阀门 `ROTATION_MAX_CONSECUTIVE_ATTEMPTS=8` → **一个死后端最多吃掉 8 × 5.5 h = 44 小时**才轮到下一个同步对。
- `_BACKEND_DEAD` 是进程内变量，跨轮不保留 → 每个 run 都要从头重新"发现"后端已死。

**修法**：
1. 子目录循环 / 同步对收尾处把 `_BACKEND_DEAD` 冒泡成 `SYNC_BACKEND_DEAD`（不必等 `sync_engine.sh:312`）；
2. 把熔断结论持久化到 `sync_state`（如 `backend_dead.json` + 时间戳/过期），下轮直接跳过该后端，而不是重跑 6 次。

### 缺陷 5：收尾"零成功"告警被"沿用上轮修复"计数掩盖

- 位置：`file_fix_pipeline.sh:1126-1136` 的 `_ol_round_stats_bump`，`add_ok=$(printf '%s' "$fixed_json" | jq 'length')`。
- `fixed_json` 包含 `♻ 沿用上轮修复` 条目（`:636-638` 会把它追加进 `fix_list` 与 `LAST_SYNC_FIXED_FILES_JSON`）。
- 实测：`本轮修复成效: 成功 183 · 缺失 2126 · 未修复 1943`，而 `grep -c "♻ 沿用上轮修复"` = **183**，`grep -c "✅ 修复成功 ·"` = **0**。数字一一对应。
- `openlist.yml:503` 的告警 `if [ "$ROUND_MISSING" -gt 0 ] && [ "$ROUND_FIXED_OK" -eq 0 ]` 因此**永不触发**——这道告警正是为"5 小时零产出"设计的。

**修法**：拆成两个计数（`ROUND_FIXED_NEW` = 本轮真实落盘，`ROUND_REUSED` = 沿用），告警只看前者；沿用数单独展示。

### 缺陷 6：源端清单获取失败被静默当成"零待传"

- 位置：`task_preview.sh:137-143`（源端失败 → `src_json="[]"`）对比 `:166-181`（目标端失败 → `PREVIEW_FAIL_PAIRS+1` + 通知里加"按全量估算"提示）。
- 非对称：**目标端失败会提示，源端失败连计数都没有**，直接让该同步对的待传量归零。
- 实测后果见 §3.3：一条 `add_preview_pair: 源端清单获取失败 (onedrive:1)` 让 `remaining_bytes` 掉了 2.49 TB，趋势通知里的"平均净传速率""预计清零"会据此给出假的乐观结论。

**修法**：加 `PREVIEW_FAIL_SRC_PAIRS` 计数并在通知里与目标端同款提示；`trend_capture_remaining` 在任一源端列举失败时写 `null`（口径"未知"）而不是求和。

### 缺陷 7：批次循环没有时间预算闸

- `sync_budget_stop()`（`task_engine.sh:131-134`）在同步对级（`:171`）和子目录级都有调用，但 `sync_by_file_batches` 的批次循环 `for i in $(seq 0 $batch_num)`（`task_engine.sh:1459`）**没有任何预算检查**。
- 实测：预算锚点 = 05:21:46 + 320 min = **10:41 UTC**（日志自报），而 `10:32:24` 启动了批次 2/3（3388 个文件）——距锚点仅 8.6 分钟，随后被 330 min step 超时杀掉，收尾统计被截断、`SYNC_BACKEND_DEAD` 冒泡（`sync_engine.sh:312`）也没走到。

**修法**：批次循环开头加 `sync_budget_stop && { SYNC_TIME_EXHAUSTED=1; break; }`。

### 缺陷 8：会话保持 step 的 env 兜底与 input 默认值相反

- `openlist.yml:66` 声明 `default: false`，注释（`:57-62`）说"关掉后同步结束立即 Persist 回传收摊，窗口全部给同步"。
- 但 `:565` 写的是 `SESSION_HOLD: ${{ github.event.inputs.session_hold || 'true' }}`，`:567` 的 bash 兜底也是 `:-true`。schedule 触发时 `github.event.inputs.session_hold` 为 null → **取 'true'** → 一旦这个 step 真被执行，就会 hold 5 小时。
- 近三轮该 step 均为 `skipped`（前一步「任务预览与全量同步」failure，而该 step 的 `if` 不含 `always()`）。所以目前没造成损失，但这是个与声明相反的潜在地雷。

**修法**：`|| 'false'`，或把 input 默认改回 `true` 并同步注释。
