## 0. 三个问题的直接回答

### Q1：目前这个方案怎么样？

**架构方向是对的，302 该拿的收益实测拿到了；但收尾两步有必崩缺陷，且轮换空档是比 10 秒起播大两个数量级的可用性问题。**

先说实测到的"好"：

| 实测项 | 读数 | 出处 |
|---|---|---|
| 视频流确实不经过 runner | `视频流 stream: n=7 均值 292ms 最大 845ms`——这 7 次 `/videos/` 全部是 ge2o 发 3xx 的时间，之后播放器直连 OneDrive，ge2o 日志里再无视频流量 | 34734584799 收尾统计（该轮有真实播放） |
| 直链可用率 | odlink `/stats`：`get=89 link_ok=35 link_miss=0 resolve_err=3 fallback=3`——35 次真实取链 0 次失败 | 34743346060 @11:59:06Z 实拉 |
| 快捷方式跟随生效 | `fast_path=32`（一次 Graph 路径寻址直接解析）+ `cross_drive=761`、`shortcuts=8`，OpenList 跟随不了 remoteItem 的坑已被 odlink 绕开 | 同上 |
| 链路降级链完整 | OpenList/odlink/ge2o 任一不健康自动回退 direct，watchdog 运行中每分钟探活 | 代码 + 各轮启动探针输出 |

再说实测到的"坏"（按严重度）：

1. **【P0】自续接力步骤在 HEAD 上必崩**（exit 127，`run_elapsed_seconds: command not found`），接力链断，且它承载的全部诊断归档（含唯一的客户端侧起播读数）一起丢失。§5.1。
2. **【P0】收尾 TG 通知步骤在 `bash -e` 下静默中止**（exit 1 零输出），本轮汇总通知发不出。§5.2。
3. **【P1】每轮轮换有 25–48 分钟服务空档**，且正被 `install emby` 的恢复拉长到 45 分钟级。§4.3。
4. **【P1】dir_cache 每轮从零开始**，实测覆盖率约 1/3，多数条目首次播放要付冷解析。§4.1。

### Q2：302 模式点播放后约 10 秒才出画面，正常吗？

**服务器能解释的部分最多 1.5 秒；其余 8 秒以上发生在服务器完全看不见的客户端侧，而且全库至今没有一个客户端侧读数——"正常/不正常"目前无法下结论，但可以低成本定位。**

- 有播放的那轮（34734584799，5 次真实播放）服务端三段实测合计：PlaybackInfo 9ms（最大 99ms）+ ge2o 取直链发 302 均值 292ms（最大 845ms）+ 字幕抽取均值 542ms（最大 1038ms，仅 2 次）≈ **热路径 0.4–1.5 秒**。
- 客户端是谁：`playback_reporting.db` 实拉查询，最近播放全部是 `Emby Web / Google Chrome macOS`、`DirectStream`，出口 IP 为海外代理（`50.7.250.50`、`45.149.92.22`）。客户端 → Cloudflare（实测边缘 iad03/lax05）→ runner、以及客户端 → OneDrive CDN 这两段走的是代理路由质量，本仓库改任何代码都碰不到。
- **为什么说"至今没有读数"**：HEAD 新增的 `[起播] 客户端出画` 探针（`emby.yml:1166` `probe_client_start`）输出写进 `playlog.log`，而 `playlog.log` 只在自续触发步骤归档（`emby.yml:2489`）——该步骤 HEAD 必崩（§5.1）。时序上恰好错开：**有播放的轮次是旧代码（没装探针），装了探针的轮次一次播放都没有**（09-13 14:16 +08 之后 playback_reporting.db 无新记录）。探针 0 个数据点。
- 10 秒的合理构成（估算，非实测）：客户端到服务器的多次 API 往返（每次经代理 + 隧道，数百 ms 级）× Web 播放器起播要串行打好几个请求，加 OneDrive CDN 建连/TTFB（runner 侧基线 0.20–0.33s，客户端经代理只会更差），加播放器缓冲解码。**没有任何一段是"服务器慢"能解释的。**
- 行为旁证：09-13 五次播放时长 17s / 94s / 34s / 173s / 5s，14:12–14:16 四分钟内同一部片起了三次（34s→173s→5s）——"起了就停、换个再试"的形态与起播体验差一致，但只是旁证。

**零成本定位实验（比改任何代码都值）**：播放通知里那条 `▶ 打开直链` 是同一个 OneDrive URL。同一客户端、同一网络直接打开它：
- 秒开 → 10 秒与 Emby/ge2o 无关，问题在播放器缓冲/解码；
- 也慢 → 问题在客户端到微软 CDN 的代理路由，本仓库无解；
- 直链秒开、Emby 里 10 秒 → 多出来的是额外往返（字幕、HLS 协商、二次请求），再按 §6 逐项消。

### Q3：可以改善吗？

**能，但要分清"服务器侧天花板"（约 1.5–2 秒）和"客户端侧未知数"（8 秒以上）。先修测量，再谈优化。**

| 手段 | 预期收益 | 代价 | 判断 |
|---|---|---|---|
| 修自续触发崩溃（补 1 行 source） | 恢复接力链 + 拿回全部诊断归档 + `[起播]` 读数可回收 | 1 行 | **必做** |
| 修通知步骤 set -e 崩溃 | 收尾通知恢复 | 3 处 `|| true` | **必做** |
| 直链对照实验 | 定位 10 秒归属 | 零 | **必做** |
| dir_cache 跨 run 持久化 | 首次播放省 ~1.5s（冷 1.75s → 热 0.29s） | odlink.py 加 dump/load | 值得做 |
| 增量备份排除 metadata imagecache | install 从 25–47min → 约 10min，直接压缩轮换空档 | 缩略图按需重建 | 值得做 |
| warm-state 字段序修正 | 海报预热不再用错误档位 | 1 行 | 值得做 |
| 加大 WU_PI_ITEMS（起播准备预热） | ≈0：实测冷 23–30ms / 热 7–9ms，三轮一致，PlaybackInfo 根本不触发 ffprobe/抽字幕 | 白打请求 | **不要做** |

## 4. 两个结构性问题（比 10 秒大）

### 4.1 dir_cache 每轮从零开始，覆盖率约 1/3

- HEAD 轮 `odlink /stats`：`dirs_cached=26367`。库内 `/onedrive/` 路径媒体文件约 8.3 万级（hy4 报告实拉 library.db 得 83,464 / 去重目录 1,837，本报告未重复拉库），目录回填上限 400。
- 代码侧佐证：odlink 的 `dir_cache` 是纯进程内 map、无 TTL（`odlink.py:287-289` 注释明说"本轮 run 内路径不会自己搬家"），**runner 一换它就清零**；而冷解析（逐段 Graph 下钻）与热路径（缓存命中后单次 Graph 取 downloadUrl）的差距约 1.5 秒。
- 顺带：目录回填串行跑，400 个用了 ~9–20 分钟（2.6s/个，受 Graph 往返限制）。

### 4.2 轮换空档 25–48 分钟，一天累计 1.5–3 小时不可用

实测交接（全部来自本次实拉的日志时间戳）：

```
34734584799 ge2o 启动 03:29:53（job 03:04:36 起）     → 上一轮 03:04 结束后空档 25.5min
34743346060 隧道就绪 07:29:06（job 06:41:06 起）     → 上轮 06:41 被取消，空档 48.1min
34743972517 job 12:00:15 起（06:56 创建排队 5h04m）  → 隧道就绪还要等约 45min install
```

空档的大头就是 §2.1 的 `install emby`：增量备份把 `metadata/**/imagecache` 缩略图一起打包（恢复日志里逐个 `Copied`，本次可见 1336+ 行），2823 个文件 / 1038MB 按每秒 1–2 个文件的速度拉，瓶颈是 OneDrive 逐文件请求延迟。**把 imagecache 从增量备份排除（或单独成包按需恢复），轮换空档能从 45min 级压到 10min 级。**

## 5. 本次确认的缺陷（按严重度，全部本报告独立验证）

### 5.1 【P0】自续触发步骤必崩（exit 127）→ 接力断 + 诊断归档全丢

- 34743346060 日志原文：`line 18: run_elapsed_seconds: command not found` + `##[error]Process completed with exit code 127.`
- 代码：该步骤只 `source "$EMBY302_DIR/lib.sh"`（`emby.yml:2454`），而 `run_elapsed_seconds` 定义在 `.github/scripts/lib/run_elapsed.sh`；对照 `backup emby data` 步骤有 `source .../lib/run_elapsed.sh`（`emby.yml:2244`）且本轮实测跑通——**唯独接力步骤漏了这行**。崩溃点 `ELAPSED=$(run_elapsed_seconds)`（`emby.yml:2467`）在 `gh workflow run emby.yml`（`:2482`）之前。
- 影响：① `gh workflow run` 永远不执行，接力只剩 cron 兜底；② 崩溃点之后的归档块（playlog.log、ge2o 分段统计、seek.log、odlink.log、wallwarm.log 等，`:2487-2556`）全部不执行——**`[起播]` 客户端出画读数恰好只存在于 playlog.log，测量做了也拿不回来**。
- 改法：`:2454` 后补 `source "$GITHUB_WORKSPACE/.github/scripts/lib/run_elapsed.sh"`。

### 5.2 【P0】收尾通知步骤在 `bash -e` 下静默中止（exit 1，零输出）

- 实测：34734584799（旧代码）与 34743346060（HEAD）两轮的 `send telegram notification` 步骤均为 exit 1，且脚本第一个输出语句（`echo "TG(收尾): …"`）从未打印——死在开头 ~65 行的某个赋值上。
- 代码：`emby.yml:2385/2386/2387` 三条 `VAR=$(grep … | tail -1 | grep …)` 管道赋值均无 `|| true` 兜底，任一 grep 无匹配 → 管道退出 1 → 赋值返回 1 → `bash -e` 立即终止整步。本机复现：`bash -e -c 'X=$(printf "abc" | grep -oE "[0-9]+"); echo after'; echo $?` → 输出 `1` 且 `after` 未打印。
- 触发条件与 wallwarm.log 内容相关（该步骤第一个 echo 之前只有这几条管道赋值可能失败），而 wallwarm.log 只在必崩的 §5.1 步骤归档（`:2555`）——**收尾通知是否存活，取决于一个谁都看不见的文件的内容**。两轮失败一轮成功（34720938292）与此吻合。
- 改法：三处补 `|| true`（或统一改 `grep -c … || true` 风格）；并把 wallwarm.log 的归档提到不依赖 §5.1 的位置。

### 5.3 【P1】warm-state.json 字段序错位 → 海报预热用"得分"当"宽度"

- 静态验证：写侧 `persist_state` 契约是 `$1="得分 宽度"`（`emby.yml:1920`，写回 `[$w,$s]`）；但 `:1935` `persist_state "$BASE"` 喂进去的 `BASE` 来自 `:1876` `.scores[]? | "\(.[0]) \(.[1])"`——文件里存的是 `[宽度, 得分]`（正确轮次写回的结果），于是 BASE 是"宽度 得分"，写回变成 `[得分, 宽度]`，**每轮启动都把文件翻转一次**。
- 日志佐证：HEAD 轮 warmup 打印 `宽度档: 9.0 3.0 1.5 4.0 6.0 13.0 7.0`——全是 ≤13 的小数（衰减后的得分），而真宽度是 `342 630 338 406 …` 量级。280 次海报预热请求全打在错误"宽度"上。
- 改法：`:1935` 改为喂 `$(printf '%s\n' "$BASE" | awk 'NF>=2 {print $2, $1}')`。

### 5.4 【P2】ge2o.log 归档会被 watchdog 探针淹没

收尾统计与归档里，ge2o.log 的 tail 大部分是每分钟一次的 `GET /emby/System/Info/Public`（127.0.0.1 自探）。odlink.log 已改为按关键行 grep（`emby.yml:2232`），ge2o.log（`:2517`）漏了同款处理——而它恰恰是"播放为何走中转"的证据源。

### 5.5 【P2】`TG_RUN_STARTED_AT` 恒为空

所有轮次的 step env 里 `TG_RUN_STARTED_AT:` 都是空串（表达式上下文被平台移除，`:383` 注释亦承认）。影响是收尾区"⏱ 已运行"退化到兜底口径，量级不大但属于"统计数字可能与直觉不符"的一处。

## 6. 起播改善路线（确认测量问题修复之后）

1. **服务器侧（账算得清的 ~1.5–2s）**
   - dir_cache 跨 run 持久化（odlink.py 加 dump/load，随增量备份走）：首次播放冷解析 1.75s → 0.29s。这是服务端唯一超过 1 秒的单项。
   - 字幕预热对准 `warm-state.json` 的 `recent` 条目（实测 0.54s/最大 1.04s，且只对首次生效）。
   - PlaybackInfo 已在 9ms 地板，不要再预热它。
2. **客户端侧（8 秒以上的未知数）**
   - 先做 §0.Q2 的直链对照实验，再决定要不要做 direct A/B（同片两模式各播一次读 `[起播]` 秒数；direct 是唯一能"用 runner 的 Azure 出口替代用户代理出口去 OneDrive"的变体）。
   - 出口 IP 实测全是海外代理、隧道边缘 iad/lax——若对照实验证明瓶颈在代理路由，仓库侧任何优化都无效，只能换客户端网络。
3. **可用性（比 10 秒更值钱）**
   - 排除 imagecache → 轮换空档 45min → 10min 级；
   - §5.1/§5.2 修好后，接力链恢复"一轮结束立刻起下一轮"的设计意图，cron 兜底 + 排队护栏（`:2473-2480`）已经写好，只欠这修复。

## 7. 结论

- **方案本身**：302 架构、降级链、预热体系、观测设计（起播等待树 / 出画探针 / 分段统计）都在正确方向上，直链可用率实测 100%、视频流确实绕开 runner。**它的问题不在架构，在工程细节**：两处必崩的收尾缺陷 + 每轮清零的 dir_cache + 被缩略图恢复拖长的轮换空档。
- **10 秒起播**：服务器可测部分 0.4–1.5 秒，不构成解释；剩余部分无任何读数。先修 §5.1（1 行）让 `[起播]` 探针的数据能落进日志，再做零成本直链对照实验——这两个动作做完，"10 秒正不正常、能不能改善"才有定量答案。
- **可证伪的预测**：正在跑的 34743972517（HEAD 代码）收尾时将复现 §5.1 的 exit 127；若 wallwarm.log 缺进度行则同时复现 §5.2 的 exit 1。下一轮有真实播放时，playlog.log 里的 `[起播] item=N 客户端出画 +Xs` 就是整份报告缺的那个数字——前提是 §5.1 先修掉。
