## 0. 三个问题的直接回答

**Q1：目前这个方案怎么样？**

架构方向是对的，而且服务端侧确实已经压得很薄——实测"点播放"这条链路上服务器自己要干的活合计 **< 1.5 秒**。但当前有两个问题：

1. **观测链路是断的**。最新提交（216a9b8）新增的客户端侧测量（`[起播]` 出画探针、`[起播等待]` 落日志）恰好被放在 `自续触发（下轮接力）` 这个步骤的归档块里，而这个步骤现在**必然崩溃**（`run_elapsed_seconds: command not found`，exit 127）→ 测量代码跑不到归档，播放证据也一起丢。同一个提交还让 `send telegram notification` 步骤在 `set -e` 下中止（exit 1，整步零输出），收尾通知也发不出去。
2. 有一个字段顺序 bug，让**每轮开头的海报墙/首屏预热用错宽度档**（实测把"得分"当成了宽度：`9.0 3.0 1.5 4.0 6.0 13.0 7.0`），280 次请求白做。

**Q2：302 模式点播放后约 10 秒才起播，正常吗？**

**服务端不是原因。** 唯一一轮有真实播放的日志（run 34734584799）里，可测的服务端各段是：

| 段 | 实测 |
|---|---|
| ge2o 处理 `/videos/`（签发 302） | n=7，均值 **292 ms**，最大 845 ms |
| Emby `PlaybackInfo`（起播准备） | n=21，均值 **9 ms**，最大 99 ms |
| Emby 抽字幕（读挂载） | n=2，均值 **542 ms**，最大 1038 ms |
| 直链 TTFB（runner → OneDrive） | n=33，均值 **0.20 s**，最大 0.89 s |

加起来不到 1.5 秒。而 302 的语义就是"302 之后视频流不经过服务器"，所以剩下的 ~8 秒发生在**服务器完全看不到的地方**：客户端 → Cloudflare 隧道的往返、客户端 → 微软 CDN 的建连与首字节、播放器缓冲与解码。

在这种拓扑下，10 秒**不算异常量级**（尤其客户端出口是海外代理/VPS 网段时，客户端到微软 CDN 那一段没有任何人管）；但也**没有任何数据能证明它是"必然"或"正常"**——判断缺一个客户端侧读数，而这个读数今天刚写进代码、一次都还没产出过。

**Q3：可以改善吗？**

分两类：

- 服务端能压的只有那 1.5 秒里的一部分：字幕 0.5~1.0 s、取直链 0.3~0.85 s。**最多省 1 秒左右**，不足以把 10 秒变成 3 秒。
- 真正能动的是**换路**：先让 `[起播]` 探针量出客户端侧到底几秒，再用 `workflow_dispatch` + `playback_mode=direct` 做一次 A/B（direct 把视频流交给 runner 的 Azure 出口中转，实测 runner → OneDrive 首字节 0.20 s）。**在量出来之前做的任何"优化"都是猜。**

把"点下播放 → 出画面"按谁在等拆开，标出哪些是实测、哪些测不到：

## 4. 判断：10 秒正常吗、能不能改善

**正常吗：在当前拓扑下，10 秒是"可能出现的量级"，但无法认定它"正常"。**

- 能认定的：**服务器不是瓶颈**（可测段 < 2 s，最坏情况）。
- 不能认定的：剩下 8 秒的构成。302 的设计**主动放弃了**对最后一段的控制与观测——这是为了省服务器带宽/CPU 换来的代价，是清醒的取舍，不是 bug。
- 一旦客户端出口是海外代理（实测每次都是），客户端 → 微软 CDN 那一段的质量完全由代理决定，**这个 workflow 无论如何改都碰不到它**。

**能不能改善：能，但天花板不高，而且必须先量。**

| 手段 | 预期收益 | 代价/风险 | 建议 |
|---|---|---|---|
| 先让 `[起播]` 探针产出数据 | 0（是测量） | 无 | **必做，第一优先** |
| A/B 一次 `direct` 模式 | 未知，可能显著 | 视频流经 runner（GitHub 出网 + Cloudflare 隧道承载视频的合规风险）；direct 下数据源 B 是唯一播放来源，而它每轮开头 ~110 s 会连续失败（§5 P1-3） | **必做**，用同一部片对比 `[起播]` |
| 把字幕预热扩到 `recent` 条目 | 省 0.5~1.0 s（仅首次抽字幕） | 每轮多几次挂载读 | 值得做 |
| 压 ge2o 取直链（③） | 已到 292 ms 均值，空间很小 | — | 不必要 |
| 加大 `WU_PI_ITEMS` | **≈0** | 每轮多打几次无意义的 `PlaybackInfo` | **不要做**（冷 23~29 ms，本来就是空的） |
| 加大头尾预热（`WU_EDGE_ITEMS`） | **≈0** | 192 MB/轮真实流量 | 保持现状（它现在只是"挂载冷读探针"） |
| 压启动恢复时间（24~47 分钟/轮） | 不影响起播，影响轮换空档 | — | 见 §5 P2-2 |

## 5. 本次排查发现的缺陷（按严重度）

### P0-1 `自续触发（下轮接力）` 必然崩溃 → 接力链断 + 归档全丢

**证据**

- run 34743346060（HEAD）步骤 `自续触发（下轮接力）` 结论 = **failure**，日志原文：
  ```
  /home/runner/work/_temp/b7fb9ba2-….sh: line 18: run_elapsed_seconds: command not found
  ##[error]Process completed with exit code 127.
  ```
- 代码：`emby.yml:2454` 只 `source "$EMBY302_DIR/lib.sh"`；而 `run_elapsed_seconds` 定义在 `.github/scripts/lib/run_elapsed.sh`（`emby.yml:2467` 调用它）。对照 `backup emby data` 步骤，`emby.yml:2241` 与 `2244` **两个文件都 source 了**。
- 该步骤以 `set -e` 运行（GitHub 默认 shell 是 `bash -e`），第 18 行的赋值失败即整步退出。

**影响（这条最要命）**

1. `gh workflow run emby.yml` 永远不会执行 → **自续接力失效**，只剩 cron `0 2,8,14,20` 兜底。
2. 崩溃点在第 18 行，而**整个诊断归档块在该行之后** → 该步骤承载的 `playlog.log`、`rclone-mount.log`（以及 ge2o/odlink/seek/warmup/wallwarm 的第二份）**全部丢失**。
3. 后果直接命中本报告的主题：**HEAD 新增的 `[起播]` / `[起播等待]` 是写进 `playlog.log` 的，而 `playlog.log` 恰好只在这个步骤归档**（`archive diagnostics` 步骤不含它）。也就是说——**测量写进去了也读不出来**。

**建议改法**：在 `emby.yml:2454` 之后补一行，与 `2244` 同款：

```yaml
source "$GITHUB_WORKSPACE/.github/scripts/lib/run_elapsed.sh"
```

### P0-2 `send telegram notification` 在 `set -e` 下中止 → 收尾通知发不出

**证据**

- run 34743346060 与 run 34734584799 的该步骤结论都是 **failure**，而 `34705718741` / `34691591428` / `34720938292` 是 success。
- 失败轮次里，该步骤的日志**只有脚本回显，没有任何真实输出**（`TG(收尾): 已构建统一版式消息` 这行从未出现，全文件只在脚本回显里出现一次）。
- 失败发生在第一个 `echo` 之前，而 `bash -e` 下能静默中止的写法只有一种：**赋值语句的命令替换返回非零**。该步骤里唯一没有保护的这类写法是 `emby.yml:2385`：

  ```bash
  WW_N=$(grep -oE '共 [0-9]+ 次图片请求' /opt/logs/wallwarm.log 2>/dev/null | tail -1 | grep -oE '[0-9]+')
  ```

  当 `wallwarm.log` 里没有"共 N 次图片请求"这行（wallwarmer 还没收尾就被收摊，或日志被 tail 截断）时，末端 `grep` 无匹配 → 管道退出 1 → 赋值返回 1 → `set -e` 立即终止整步。
- 最小复现（本机 bash 5.3.15）：
  ```
  $ bash -e -c 'X=$(echo "" | grep -oE "[0-9]+"); echo after'; echo EXIT=$?
  EXIT=1                     # after 没打印，确认中止
  $ bash -e -c 'A=""; [ -n "$A" ] || A=$(echo "" | grep -oE "[0-9]+"); echo after'; echo EXIT=$?
  EXIT=1                     # 下一行 2386 的兜底同样会中止
  ```

**影响**：收尾汇总通知（状态/模式/本轮直链/海报预热/数据备份/播放客户端）整条丢失，用户看不到"这一轮干了什么"。

**建议改法**：两处都补兜底。

```bash
WW_N=$(grep -oE '共 [0-9]+ 次图片请求' /opt/logs/wallwarm.log 2>/dev/null | tail -1 | grep -oE '[0-9]+' || true)
[ -n "$WW_N" ] || WW_N=$(grep -oE '已预热 [0-9]+ 请求' /opt/logs/wallwarm.log 2>/dev/null | tail -1 | grep -oE '[0-9]+' || true)
```

（同类风险建议全库扫一遍：所有 `VAR=$(… | grep …)` 且没有 `|| true` / `|| echo` 兜底的地方，在 `bash -e` 下都是定时炸弹。）

### P1-1 `warm-state.json` 字段顺序颠倒 → 每轮开头的海报墙预热用错宽度档

**证据链**

1. 线上文件（rclone 直读）是 **`[宽度, 得分]`**：
   ```json
   {"updated":1789308567,"scores":[[342,6.5],[630,4.5],[338,3.5],[406,3.0],[490,2.0],[624,1.5]],"recent":[…]}
   ```
2. 读它的代码（`emby.yml:1876`）按 `[宽度, 得分]` 取：
   ```bash
   BASE=$(jq -r '.scores[]? | "\(.[0]) \(.[1])"' "$STATE")   # → "342 6.5"（宽度 得分）
   ```
3. `emby.yml:1880` 的 `DECAYED` 保持同一顺序（输出 `$1` 与 `$2*衰减`）→ 仍是"宽度 得分"。
4. 但写回函数（`emby.yml:1920-1934`）的契约是 **`# $1="得分 宽度"多行`**，内部 `read -r s w` 后写 `[w,s]`。
5. `emby.yml:1935` 在启动时调用 `persist_state "$BASE"` —— **把"宽度 得分"喂给了期望"得分 宽度"的函数**。
6. 本机复现（复刻 `persist_state`）：

   ```
   输入（BASE，宽度 得分）:  342 6.5 / 630 4.5 / 338 3.5
   衰减后（DECAYED）      :  342 3.2 / 630 2.2 / 338 1.8
   persist_state "$BASE" 写回: {"scores":[[2.2,630],[3.2,342],[1.8,338]]}   ← 字段被换位
   对照 persist_state "$MERGED"（得分 宽度）: {"scores":[[342,129.5],[630,4.5]]}  ← 正确
   ```
7. 日志佐证：run 34743346060（HEAD）的预热打印
   ```
   海报墙/首屏预热宽度档: 9.0 3.0 1.5 4.0 6.0 13.0 7.0
   海报墙预热完成: 280 次请求
   媒体库首屏预热完成: 共 3423 张
   ```
   40 条 × 7 档 = 280 —— 这 7 个"宽度档"全是小数，是**得分**被当成了宽度。对照 run 34734584799 同一位置打印的是 `342 630 338 406 490 624 494 620`（真宽度）。

**影响**

- 每轮开头的海报墙 + 媒体库首屏预热（本轮 280 + 3423 次请求）打在 `maxWidth=9 / 3 / 1.5 …` 这种无意义尺寸上，**缓存键与客户端实际请求对不上 → 白做**。设计意图是"点开就热"，实际是冷的。
- 只有当轮内客户端真的产生了图片请求、`merged_sizes` + `persist_state "$MERGED"` 跑过之后，文件才被**修正回正确顺序**。所以在"没人看图"的轮次里，错位会一直传递到下一轮。
- 也能解释为什么 34720938292 / 34705718741 两轮打印"宽度档: 无（跳过）"——错位几轮之后得分被反复 ×0.5 衰减到 <1 全被淘汰，档位表空了。

**建议改法**：最小改动是在 `emby.yml:1935` 换序，其余不动：

```bash
persist_state "$(printf '%s\n' "$BASE" | awk 'NF>=2 {print $2, $1}')"
```

或把 `persist_state` 的入参口径统一成"宽度 得分"（同时改 `merged_sizes` 的输出顺序，改动面更大，不推荐）。

### P1-2 `ge2o.log` 归档仍是纯 `tail` → 被 watchdog 探针占满，播放证据永远看不到

**证据**：run 34743346060（HEAD）里 `--- ge2o.log (tail 80, 脱敏) ---` 段落的 80 行**全部**是：

```
[ge2o:v2.8.2] 2026-09-13 19:58:23 | 200 | 704.478µs | 127.0.0.1 | 8095 .* | GET /emby/System/Info/Public
```

watchdog 每 60 秒打一次这个探针（`emby.yml:952-1007`），80 行 ≈ 最近 80 分钟。`自续触发` 里的 `tail -n 60`（`emby.yml:2517`）同理。

**影响**：直接挡住了两个问题的回答——

- 那条 **35.7 秒**的请求是什么（`其它: n=665 均值 122ms 最大 35683ms`，这一轮唯一的大头，也是用户最可能感知为"点了没反应"的东西）；
- 4 次播放各自的 302 行、客户端 IP、请求时刻（本来可以拿它和 `playback_reporting.db` 的 `开始播放` 时刻对齐，量出"请求 → Emby 认定开播"的间隔）。

**有意思的是**：HEAD 提交已经对 `odlink.log` 做了这个修复（改成按关键行 grep，提交信息里写了理由），但**漏了 `ge2o.log`**——而 `ge2o.log` 恰恰是 302 链路的证据源。

**建议改法**：照 `odlink.log` 的做法，改成按关键行 grep 再 tail，例如：

```bash
grep -aE '\| (3[0-9]{2}|2[0-9]{2}) \|' /opt/logs/ge2o.log | grep -avE '127\.0\.0\.1.*System/Info/Public' | tail -n 60 | redact_log
```

（排除自身探针 + 保留客户端请求行。）

### P1-3 数据源 B（Sessions 轮询）每轮开头有 ~110 秒的连续失败窗口

**证据**：三轮日志里形态完全一致，且都出现在启动后约 10 秒起、连续 11 次、之后不再有输出：

```
Emby 认证矩阵: System/Info(头)=200 | Sessions 头X-Emby-Token=200 查询api_key=200 头X-MediaBrowser-Token=200 头Authorization=200
Emby Sessions 自检: http=200 会话数=1 认证方式=header
[WARN] Sessions 查询失败 http=000（第 1 次）
[WARN] Sessions 查询失败 http=000（第 11 次）
```

`http=000` 是 curl 失败（`-m 8` 超时或连接失败）。注意**紧挨着的认证矩阵四种方式全部 200**，说明不是认证问题；时间窗与 warmup 的重活（冷挂载读 + 三千多次图片请求）重叠。计数器只在 `%10==1` 时打印，所以"第 1 次、第 11 次"代表连续 11 次失败（约 110 秒）。

**影响**

- 302 模式下这只是兜底源（主源是 ge2o 日志），影响有限。
- 但 **`direct` 模式下它是唯一的播放来源** —— 那 110 秒内发生的播放不会被记录、不会发通知。做 A/B 测试时要避开这个窗口。
- `-m 8` 且无重试，遇到 Emby 忙就整轮跳过，没有降级策略。

**建议改法**：超时放宽（如 `-m 20`）+ 首次失败重试一次；或把"连续失败"窗口在日志里明确收尾（打印一行"已恢复"，避免"死了"和"恢复了但没输出"无法区分）。

### P2-1 「起播准备预热」与 302 起播无关

实测冷 23~29 ms、热 7~11 ms（三轮一致），说明 `PlaybackInfo` 不做 ffprobe / 不抽字幕（媒体信息在库扫描时已入库）。**"连打两次把探测/抽字幕提前做完"的设计意图实测不成立。** 关键路径上的字幕是独立请求（均值 542 ms / 最大 1038 ms）。

建议：不要再加大 `WU_PI_ITEMS`；若要压字幕，应把 `recent` 里的条目（`warm-state.json` 的 `recent` 已有 7~12 条）纳入针对性预热，而不是继续打 `PlaybackInfo`。

### P2-2 每轮启动恢复 24~47 分钟，其中图片缓存是主要浪费

- 实测 `install emby`：1471 s / 1659 s / 2833 s / 1492 s。
- 恢复链修好之后（HEAD 已修 `RESTORED_FROM` 被无条件清空的问题），当 live 增量恢复成功时，全量包**仍然要整条 zstd 流式解压一遍**才能取出 `./cache`（zstd 不支持随机访问，代码注释自己也承认"省不掉那几分钟"）。
- 建议：把图片缓存单独成包或单独目录同步，让"关键数据恢复完 → 起服务"不必等整包解压。

### P2-3 「取链自检」的结论只进 TG，不落日志

`MAP_CN`（`emby.yml:902-911`）只被 `tg_add_kv` 用掉，日志里只有一行 `直链映射探针: 已取到媒体库目录`。事后无法复核"那一轮自检到底是通过还是未检测"。建议把 `MAP_PROBED` / `MAP_OK` 也 echo 一行。

### P2-4 `install emby` 的 2833 s 是否回归，需要一次干净对照

HEAD 那轮 `install emby` 从 24~28 分钟涨到 **47 分钟**，但当前在跑的 HEAD 轮是 24 分 52 秒。所以更像 OneDrive 侧限流的方差，而不是恢复链改动引入的回归——但**在下一轮 HEAD 跑完后值得再核一次**，别把方差当结论。
