# Telegram 通知规范（全库唯一真源）

全库所有 Telegram 通知的**版式与发送规则**都在这里找答案。

**这是风格指南，不是军规。** 绝大多数条目是「建议 + 为什么 + 反例」，目的是让你在没有
先例可循时也能写出和别人风格一致的通知。只有「版式构件 · 收尾区」「实现与接线 · 接线」
「发送层要求」「验证与交付」四处是硬约束，不遵守会造成通知丢失或误判失败。

改动流程：版式改动**先改这份文档，再同步实现**；实现改完跑一遍渲染预览（规范 · 渲染预览）。
新增 / 改名 / 下线通知**不需要登记任何文档**——逐条清单用脚本现场枚举：

```bash
bash skills/telegram-notify-audit/scripts/list_notify.sh
```

域级出口与档位规则（哪类通知走哪套实现、什么算重要档）在
[`telegram-notify-registry.md`](telegram-notify-registry.md)（引用写「台账」）。

配套 skill（在仓库根 `skills/` 下）：写新通知用 `telegram-notify-send`，
核对全库版式用 `telegram-notify-audit`。

**引用本规范时写「规范 · 主题名」**（如「规范 · 折叠行」「规范 · 取值行口径」），
不要写章节号——章节号会随文档重排变化，主题名不会。

## 1. 设计原则

### 1.1 一条通知要回答三个问题

> **发生了什么 / 影响多大 / 我要做什么**

写通知前先过一遍这三问，比纠结用哪个 emoji 更有价值：

- 发生了什么 → 标题（emoji + 短语）+ 状态 kv
- 影响多大 → 计数与量化（失败 3 个 / 减少 100 GiB / 跳过 12 条）
- 我要做什么 → 复制即用命令块、下一步说明、运行日志链接

### 1.2 视觉层级靠三件套

| 手段 | 承担的作用 |
|---|---|
| 分隔线（18 条全角横线 `━`） | 标题锚点 |
| 空行 | 段落与分节的边界（只有固定几处产生，见规范 · 空行的来源） |
| emoji | 语义与状态的彩色锚点 |
| 等宽 `<code>` | 「这段可以直接复制」的机器值 |

不使用 `<b>` 与 `<i>`（全库禁用）：上面三件套已经给足了区分度，而且省掉「哪里该加粗」的判断
成本（条目主体和 kv 值的边界很难说清）；另外 `<i>` 对中文几乎看不出效果，只会让
HTML 变复杂。

### 1.3 只有三种标签

| 标签 | 用在哪 |
|---|---|
| `<code>` | 机器值：路径、文件名、命令、密码、IP、ID、端口、原始异常串 |
| `<pre>` | 多行块：日志、复制即用命令、异常栈（保留换行、整块复制） |
| `<a>` | 链接：收尾区运行日志、订阅源、播放直链 |

其余一律裸文本——但动态内容要**转义**（`& < >` 会触发 400，见规范 · 发送层要求）。

#### 取值行口径

一条取值行（`标签：值`）用等宽还是裸文本，只看一件事——**它是不是
机器返回的值**。

| 值的性质 | 口径 | 例 |
|---|---|---|
| 机器返回（IP、ISP、ASN、位置、主机名、域名、版本、ID、端口、路径、文件名、命令、原始异常串） | `<code>` | `位置：<code>Tokyo, JP</code>` |
| 自然语言（原因、状态描述、结论、备注） | 裸文本 | `状态：部分失败` |

判据取「来源」而不是「值值不值得复制」：一次归属查询返回的 IP / ISP / ASN / 位置
同属一批机器返回值，建议整节同为等宽；若按「ISP 和位置没人会去复制」逐个判断，
同一节就会变成「IP 等宽 → ISP 正体 → ASN 等宽 → 位置正体」的斑马纹，读者只会
理解成版式出了 bug。计数、时长、状态这类人写的结论值本来就裸文本，不受这条影响。

### 1.4 统一优先于个性

同一类信息在不同子系统里形态一致，读者才能跨通知扫读。因此版式尽量走真源助手
（规范 · 助手速查），而不是各脚本自己拼字符串。

### 1.5 说人话，术语留日志

通知的读者不一定是实现者。**凡是读者要「看懂」的字段，一律用日常说法**——失败原因、
状态、结论、说明段都属于这一类：

| 别写（内部机制） | 写成（人话） |
|---|---|
| 后端写熔断，未探测 | 存储端本轮整体故障，未试写 |
| 已重启容器复核 | 已复核确认 |
| 短哈希目录 / base64URL 目录 | 备用目录 / 编码目录 |
| 目标目录不可写（原目录与短哈希目录均未通过可写性预检） | 目标目录不可写（存储端本轮整体故障，未试写；备用目录也写不进去） |

判据是「**这句话是给实现者排查用，还是给读者做判断用**」：排查用的细节（`rc=1`、
`HTTP_CODE:200`、缓存口径、容器重启、方法名与黑名单）全部留在运行日志里，通知只给
结论与下一步。把日志原样搬进通知（尤其是搬成条目子行）会把一条通知撑成几十行，
同时把结论埋在中间——这是最难看的形态。

术语不是不能出现，是要**有边界**：`<code>` 里的路径、命令、原始异常串照旧原样输出
（规范 · 只有三种标签），那是可复制可搜索的机器值；被翻译的只有「需要读者理解」的自然语言字段。

## 2. 版式构件

每个构件给出：形态 → 用处 → 助手 → 建议与反例。助手的跨语言对照见规范 · 助手速查。

### 2.1 标题与分隔线

```
{emoji} 标题
━━━━━━━━━━━━━━━━━━
```

- 助手：`tg_add_title`（bash）；pwsh / python 用 `TG_SEP` 手拼。
- 建议：emoji + 短语，状态与细节下沉到 kv 行；标题后紧跟分隔线、不空行。
- 分隔线恒为 18 条全角横线；三套发送层（bash / pwsh / python）与 `sync_to_tg.sh`
  内嵌的一份共四处定义同值，不要自造。
- **同一套流程被不同来源触发时，标题要能区分来源**（先例：OpenClaw 的「最终归档告警」）。
  形态为 `{emoji} {来源标签} · {原标题}`，标签与原标题之间用 ` · ` 连接；
  来源标签由触发方经环境变量传入，**留空时标题保持原样**（定时轮不受影响）。
  现有实例：proxy 测速三套的 `PROXY_SPEEDTEST_LABEL` —— 被
  `proxy-speedtest-gistnodes` 调用时传 `gist 节点`，标题变成
  `✅ gist 节点 · 泰尔三网测速`，与它自己的定时轮区分开。标签只拼**主报告**标题；
  ❌ 异常退出 / ⛔ 异常终止兜底标题不带 label（兜底是步骤级诊断，与触发来源无关）。

### 2.2 kv 行

```
标签：值
```

- 助手：`tg_add_kv`（值自动转义，裸文本）。
- 建议：全角冒号；多个字段用 ` · ` 连接。
- 一行塞多个字段时，用全角冒号标签打头作锚点（`规格：` / `链路：` / `客户端：`），
  避免无锚点的裸 ` · ` 串。

### 2.3 机器值

```
路径：<code>/mnt/media/a.mp4</code>
```

- 助手：`tg_add_path`。
- 建议：路径 / 文件名 / 命令 / 密码 / IP / ID / 端口 / 原始异常串一律等宽——读者一眼
  看出「这段可以直接复制」。判据见规范 · 取值行口径。

### 2.4 分节

```
{emoji} 分节 · N
```

- 助手：`tg_add_section`（段前自动空行；紧跟分隔线时自动不空行）。
- 建议：**分节后跟条目列表时带计数 ` · N`**（规模一眼可见）；后面是 kv 行或单段说明
  时可以不带。
- 反例：`❌ 失败清单`（后面是 3 条条目却没有计数）。

### 2.5 条目与树形

```
  ├─ <code>video_a.mp4</code> · 1.7 GB · 2160p
  └─ <code>video_b.mp4</code> · 重试修复失败
```

- 助手：`tg_entry`（单行）/ `tg_add_entry`（累积多行）；双机器值用 `tg_entry_pair`
  （`→` 替换关系）或 `tg_entry_codes`（`·` 并列）；与 `tree_lines` 组合成树形条目流。
- 建议：条目一律 `├─/└─` 树形；元数据用 ` · ` 分隔、放在主体之后。
- 注意：`$(tg_entry …)` 不输出尾换行，命令替换还会吃掉它，**累积多行请用
  `tg_add_entry`**——否则条目会粘成一坨。
- 树形前缀统一包等宽 `<code>`（`<code>  ├─ </code>`）：正文区是比例字体，空格与盒线
  字符宽度各异，裸文本前缀的竖线列必然错位；包进等宽区后 `├─/│/└─` 严格成列。
  手拼前缀同样包 `<code>`。
- 反例：`• video_a.mp4` 平铺。

### 2.6 折叠行

```
  └─ 还有 8 条…
```

- 助手有两个，按**输入是裸文本还是已构建条目流**选，选错会造成二次转义：

  | 助手 | 输入 | 做什么 |
  |---|---|---|
  | `tree_code_fold` | 裸文本（未转义、无标签） | 逐行转义 + 套 `<code>` + 超上限折叠 |
  | `tree_fold` | 已由 `tg_add_entry` / `tg_entry` 构建的条目流 | **只**截断 + 加折叠行 |

  对已含 `<code>` 的条目流误用 `tree_code_fold`，会把 `&` 转成 `&amp;amp;`、并把
  `<code>` 本身转义掉。
- 建议：折叠行并入条目流作末条（由 `tree_lines` 统一决定 `└─`），不要单独补一行造成
  双 `└─`。

**折叠与否看清单性质，不只看条数**：

| 清单性质 | 超上限怎么办 | 例 |
|---|---|---|
| 流水 / 日志类（读者只需知道规模，单条价值低） | 折叠为「还有 N 条…」 | 已上传文件、删除的重复文件、排除规则、日志行 |
| 结构性清单（读者要逐条核对，少一条就漏了结论） | **全量展示，不折叠** | 任务预览的同步对、进度面板的五组任务列表、批次统计清单 |

判据是「折叠掉后半段会不会让读者误判」，不是「列表长不长」。结构性清单若确实很长，
靠分节计数 ` · N` 交代规模即可——把「失败了哪些」折叠成「还有 N 条…」，等于把读者最
需要看的部分藏起来。

**二层列表（条目 + 子行）不在 `tree_fold` 适用范围内**：`tree_fold` 按「行」截断，而
带子行的列表截断单位是「条目」（1 条目行 + N 行子行），按行截断会把子行切在半路。这类
列表由调用方按条目计数并自行补折叠行（用 `tree_sub` 缩进），折叠行仍并入条目流作末条。
实例见任务预览的条目子行（`差异构成：` / `排除 · N`）与去重通知的方法摘要。

**子行是给一个条目补一句话，不是给日志开口子**：往子行里灌原始日志，单文件就能撑出
十几行（源/目标全路径、rclone 原始报错、内部机制术语），是通知里最难看的形态，而且
结论会被埋进噪音里。失败原因写进条目行的元数据、一句人话说完（规范 · 说人话），
要看过程的读者走收尾区的运行日志链接。

### 2.7 多行块（日志 / 命令）

```
<pre>gh workflow run openlist.yml -f run_mode=同步</pre>
```

- 助手：`tg_add_pre`（转义 + `<pre>` 包裹）；`tg_add_block` 只用于已含标签的片段。
- 建议：日志、异常栈、复制即用命令用 `<pre>`（保留换行、整块复制）；不要用它替代行内
  `<code>`。
- 原始输出建议取**尾部 1200 字节**：超长输出会让 `<pre>` 跨分片边界。bash 真源的
  分片会在边界自动闭合/重开标签（规范 · 发送层要求），但 python 侧分片不做标签闭合，标签断开
  即破版——按尾部 1200 字节执行就不依赖这套差异。

### 2.8 说明段

```
如确认无误，请手动触发 force_sync=true
```

- 助手：`tg_add_note`（段前自动空行）。
- 建议：说明、备注、免责声明用独立说明段，与数据区分开。注意该助手对整段转义，
  **段内不能携带 HTML 标签**。

### 2.9 收尾区（硬要求）

```
⏱ 已运行 22 分钟 · 🔗 <a href="…">运行日志</a>
```

**硬要求**：所有通知都要有收尾区，唯一例外是媒体 caption（规范 · 媒体 caption）与
常驻服务的 `🕒` 报告时刻形态（见本节末「常驻服务例外」）。进度面板每次刷新
都带收尾区，时长只从这里出。

必须用 `tg_add_footer` / `Get-TgFooter` / `tg_footer_line`，不要手拼——助手已处理空行、
降级与链接。附加链接可用 `tg_add_footer <var> "标签" "URL"` 追加多个 `· 🔗 <a>`。

- 语义是 **run 已运行时长**，不是步骤自身耗时；格式见规范 · 时长的五层。
- 降级链（三套实现一致）：runner 开机时刻兜底 → 取不到则不显示时长；
  `TG_RUN_URL` 缺失则整行跳过。`TG_RUN_STARTED_AT` 变量保留仅为兼容历史注入与
  本地测试覆写，**workflow 不要注入它**（见规范 · 接线）。
  - 兜底口径按 **job** 计时（hosted runner 的 PID 1 随 job 启动，误差秒级），
    与 job 硬上限 6h 同口径。
- **常驻服务例外（无 run 上下文）**：看板 `board.py`、哨兵 `gateway-watchdog.py`
  与健康看门狗 `health/system_health.sh` 这类本机常驻进程没有 GitHub run（前两者在
  宿主机 `/dropbox/self-hosted/quota-board/`，不在本仓库），「已运行」按开机时刻兜底
  会把**主机开机时长**误报成服务时长。这类通知的收尾区固定为**报告时刻**：
  `🕒 2026-11-06 19:32（东八区）`（时间格式见规范 · 日期与相对时间），仍属「必须带
  收尾区」的硬要求，只是语义从 run 时长换成事件发生时刻。`🕒` 只用于此处，
  不要与 `⏱` 混用。

**接线（硬要求）**：workflow 必须在 job 或 step 级 env 注入 `TG_RUN_URL`，否则通知没有
日志入口：

```yaml
env:
  TG_RUN_URL: https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

- **不要注入 `TG_RUN_STARTED_AT: ${{ github.run_started_at }}`**。`github` 上下文没有
  `run_started_at` 属性（官方属性表只有 `run_id` / `run_number` / `run_attempt`），
  表达式对不存在的属性求值为**空串**，注入即等于声明一个永远取不到的源，属于死配置；
  助手侧的 `/proc/1` 兜底无需任何注入即可工作。

配合 `if: ${{ always() }}`——通知写在业务块末尾而没有 `always()`，任务失败时反而收不到
通知。

**业务步内嵌通知怎么处理**（判据，不是硬约束）：通知写在业务块末尾、失败就走不到时，
按两件事决定是否拆成独立 `always()` step——

| 场景 | 处理 | 理由 |
|---|---|---|
| 消息只依赖**落盘产物**（如 `/tmp/*.note`、状态文件） | **拆**成独立 step，读文件重建消息 | 失败也不丢，且不必搬运行时变量 |
| 消息依赖**同一 shell 的运行时变量** | 在业务步内加**失败兜底分支**；不拆 | 拆步要落盘全部状态，代价大于收益 |
| 通知语义是「服务/监听已就绪」 | **不拆** | 启动失败时发「已就绪」是错的；收尾的停止通知已闭环 |
| 长驻循环内的逐事件通知（如播放通知） | **不拆** | 循环没起来就没有事件可报 |

反例：给整个业务 step 加 `if: always()` 让它失败后重跑——挂载都失败了还照常跑下载/去重，
比静默更糟。

### 2.10 空行的来源

只有这几处会产生空行，其余地方建议不要手写 `\n\n`：

1. `tg_add_section` 段前
2. `tg_add_note` 段前
3. `tg_add_footer` 前
4. **正文与动作行之间**（如「▶ 打开直链」超链接），由调用方补——先判断正文是否已有尾
   换行，避免产出双空行
5. **多组列表的组与组之间**（任务预览的源端分组、去重通知的重复组）。这是唯一允许
   手写的空行，但**必须带条件**：只在前面已有组时才补。首组之前也补一次，分节标题与
   首组之间就会多出一个空行。

分隔线与紧随其后的内容之间不空行。

## 3. 通知形态（九类）

写新通知时判断它属于哪类形态，照对应的示例与要点来；具体某个线上通知长什么样，
用脚本现场枚举（见文档开头），或直接搜实现里的标题字面量。

| 形态 | 典型场景 | 要点 |
|---|---|---|
| 结果通知 | 备份 / 同步 / 测速 / 分卷等任务收尾 | 标题状态 emoji 随结论降级，共用一条发送出口 |
| 清单明细 | 已同步文件、失败清单、账号池 | 流水类折叠、结构性清单不折叠（规范 · 折叠行） |
| 复制即用命令块 | 跳过通知给 force_sync 命令、还原入口 | 分节 + 说明段 + `<pre>` 命令块 |
| 失败与异常兜底 | 未捕获异常、信号终止、可控失败 | 极简形态，必须留痕，先恢复环境再发 |
| 告警通知 | 归档失败、网关启动失败、存储失效 | 对象机器值 + 结论原因裸文本 + `<pre>` 收尾 |
| 入口与凭据 | Runner 就绪推 SSH/RDP/出口网络、改密回执 | 按套分节，整节同为等宽机器值 |
| 进度面板 | openlist 同步进度原地刷新 | 唯一需要 message_id 的场景（删旧 + 发新） |
| 带动作行 | 播放通知的「▶ 打开直链」 | 正文与动作行之间补一个空行 |
| 媒体 caption | 随视频发出的说明 | 无标题/分隔线/收尾区，收尾区唯一固有例外 |

### 3.1 结果通知

建议顺序：**标题（状态 emoji）→ 关键 kv（对象 / 状态 / 计数）→ 明细分节 → 收尾区**。
状态与结论下沉到 kv，标题只说「谁 + 怎么了」。

多分支时**共用一条收尾与发送出口**，不要每个分支各发一次：

```bash
case "$STATUS" in
  cancelled) tg_add_title msg "⛔ 任务已中断"
             tg_add_note  msg "任务被取消，数据未受影响；如需继续请重新运行。"
             tg_add_footer msg; send_tg "$msg"; exit 0 ;;   # 提前返回，避免二次追加
  success)   tg_add_title msg "✅ 备份成功"; tg_add_kv msg "状态" "完成" ;;
  *)         tg_add_title msg "❌ 备份失败"; tg_add_kv msg "状态" "失败" ;;
esac
tg_add_footer msg
send_tg "$msg" || echo "::warning::TG 通知发送失败（不影响任务）"
```

```
✅ 备份成功
━━━━━━━━━━━━━━━━━━
日期：2026-09-10
文件：<code>backup.tar.gz</code>
大小：1.150 GiB
状态：完成

⏱ 已运行 18 分钟 · 🔗 运行日志
```

要点：

- 状态图标随结论降级——0 成功、数据缺失、中止，都该降为 ⚠️ / ❌，不要恒 ✅。
- 降级依据是**本轮发生的事**，不是库存里的历史累计数：拿累计数判定会让通知永久标黄，
  读者分不清「这轮出事」还是「旧账没清」。累计数放 kv 并标注「（累计）」。
  （反例：ph-dl 收尾曾按累计损坏数降级，导致 0 下载的空转轮次也报 ⚠️。）
- 发送失败用 `|| echo "::warning::…"` 或 `|| true` 留痕，**不要** `>/dev/null` 吞掉（规范 · 发送层要求）。
- 步骤带 `if: ${{ always() }}`，否则任务失败时反而收不到通知。

### 3.2 清单明细

先按状态或原因**分组**（组头 + 计数），再树形列出条目：

```
📋 处理结果 · 3
📁 onedrive:media
  ├─ <code>电影/A.mkv</code> · 3.1 GiB
  └─ <code>电影/B.mkv</code> · 800 MiB

📁 onedrive:backup
  └─ <code>backup.tar.gz</code> · 1.150 GiB
```

要点：

- 流水类清单每组建议上限 8 条，超出折叠为「还有 N 条…」；结构性清单不折叠（规范 · 折叠行）。
- 组内还有附属明细时降为二层列表（`│ ` 前缀 + 缩进 2 格的 `├─/└─`）：子行前缀必须与
  条目前缀**等宽**（`tree_sub` ≡ `tree_conn`，各 5 字符），否则子行正文比条目正文右移
  一格；子行只补一句话，不搬日志（规范 · 折叠行）：

  ```
  📁 onedrive:backup
    ├─ <code>aliyundriveCrypt/backup</code> · 源端 36.065 GiB / 1415 文件 · +7.268 GiB / +2 文件
    │  差异构成：新增 1 · 同名更新 1
    └─ <code>aliyundriveCrypt/media</code> · 无变动
  ```

- 失败清单则**不挂子行**：原因写进条目行的元数据，一句人话说完。

  ```
  ❌ 无法同步文件 · 2
    ├─ <code>media/大文件A.mkv</code> · 超过 45 GiB，需分割后重传
    └─ <code>media/fSWP4H4.jpg</code> · 目标目录不可写（存储端本轮整体故障，未试写；备用目录也写不进去）
  ```

- **空清单整段跳过**，不要渲染成 `✅ 已处理 · 0`——图标与计数自相矛盾。零计数的分节
  同理，用 `if [ "$n" -gt 0 ]` 包起来。

### 3.3 复制即用命令块

给人**可复制执行的命令**，而不是数据文件路径（marker / JSON 是人读不懂的落盘载体）。
固定形态是「分节 + 描述说明段 + 命令块」，多条命令重复这一组：

```
🛠️ 复制即用

▸ 强制同步（全量，含本任务）
<pre>gh workflow run openlist.yml -f run_mode=同步 -f force_sync=true</pre>

▸ 还原 3 个非原名文件
<pre>gh workflow run openlist.yml \
  -f run_mode='⚠️ 还原 · 修复文件还原为原路径' \
  -f restore_task=media</pre>
```

参数值要按实际匹配逻辑核实（例如 `restore_task` 按 marker 文件名首个 `_` 前缀匹配，
填完整任务名反而匹配不到）。多行命令用 `\` 续行，整块可直接复制。

### 3.4 失败与异常

- 中文阶段或原因写清楚；原始异常串用 `<code>`；多行日志用 `<pre>`（尾部 1200 字节）。
- 英文 token 与错误码建议中文化：`退出码 45` 而不是 `exit=45`。
- 建议给出下一步动作（复制即用命令，或「见运行日志」）。

```
❌ 下载失败
━━━━━━━━━━━━━━━━━━
文件：<code>video_a.mp4</code>
耗时：12.34 秒

📦 大小
源端：1.150 GiB · 已传：300 MiB

📄 rclone stderr
<pre>ERROR : Failed to copy: connection reset</pre>

请检查源端可用性后重跑本任务。

⏱ 已运行 5 分钟 · 🔗 运行日志
```

**异常与信号兜底分支**是最容易写坏的一块。形态可以极简（标题 + 原因 + 收尾区）：

```
❌ 泰尔三网测速异常退出 · 环境准备失败
━━━━━━━━━━━━━━━━━━
原因：<code>TUN 启动超时：mihomo 未在 30 秒内就绪</code>

⏱ 已运行 1 分钟 · 🔗 运行日志
```

要点：

- 兜底分支**必须留痕**。python 侧统一走 `notify_best_effort(stage, msg)`（内部取返回值
  并记日志）；直接 `send_telegram(...)` 后 `except: pass` 会同时吞掉异常和返回值，
  限流与 400 时完全没有痕迹。
- 发送前先恢复环境（例如先撤 TUN 再发），否则连 API 都送不出去。

### 3.5 告警通知

形态固定为「对象（机器值）+ 结论 / 原因（裸文本 kv）+ 原始输出（`<pre>` 分节）」：

```
⚠️ 归档告警 · OpenClaw 主包
━━━━━━━━━━━━━━━━━━
对象：<code>openclaw.tar.gz</code>
结论：上传失败 · 退出码 2
原因：rclone 上传失败
Run ID：<code>12345678</code>

🧾 原始输出
<pre>2026/09/12 09:00:00 ERROR : Failed to copy: connection reset</pre>

⏱ 已运行 41 分钟 · 🔗 运行日志
```

要点：

- 对象是包名、标签这类机器返回值 → `<code>`；结论与原因是人写的 → 裸文本。
- 分节后跟 `<pre>` 时**不带** ` · N`（计数只用于条目列表）。
- `<pre>` 是正文最后一块，其后只跟收尾区。

### 3.6 入口与凭据

按套分节（SSH / RDP / 出口网络），每套内的取值行**整节同为 `标签：<code>值</code>`**
（规范 · 取值行口径）：出口网络的 IP / ISP / ASN / 位置都是同一次查询的机器返回值，
一律等宽；有效期与共用说明是自然语言，走说明段并保持裸文本。

```
🟢 Windows runner 已就绪
━━━━━━━━━━━━━━━━━━
🔐 SSH · 3
  ├─ 命令：<code>ssh runner@example.ts.net</code>
  ├─ 域名：<code>runner.example.ts.net</code>
  └─ 备用 IP：<code>100.64.0.1</code>

🖥️ RDP · 3
  ├─ 地址：<code>runner.example.ts.net:3389</code>
  ├─ 用户：<code>runner</code>
  └─ 密码：<code>********</code>

🌐 出口网络 · 4
  ├─ 出口 IP：<code>203.0.113.7</code>
  ├─ ISP：<code>Contoso</code>
  ├─ ASN：<code>AS64512 · Contoso</code>
  └─ 位置：<code>Tokyo, JP</code>

有效期：约 6 小时 · 超时自动结束

ℹ️ 域名固定不变 · IP 每次运行会变，仅作备用 · 密码 SSH/RDP 共用

⏱ 已运行 2 分钟 · 🔗 运行日志
```

分节 emoji 不要与标题 emoji 重复（标题已是 🖥️，分节就用 🔐 / 🌐）。

凭据通知**没有特殊发送通道**：照样用 `tg_add_*` 构建（密码走机器值口径自动等宽 +
转义）再发。不要为凭据自造「单发不重试」的实现——429/400 都意味着上一条没被
Telegram 收到，放弃重试只会让凭据彻底丢失。

### 3.7 进度面板（原地刷新）

- 标题：刷新态 `🔄 同步进度`；终态按**严重度从高到低**判定——`⛔ 同步中断`（一个
  任务都没注册，注册前就被取消/失败）> `⏸️ 同步轮次收摊`（还有待处理/进行中：时间
  预算到站或撞 6h job 上限，剩余任务下轮自动接力，属预期内收摊而非事故）> `⚠️ 同步
  完成`（有失败）> `✅ 同步全部完成`（无失败，若有文件经修复落盘则在副标题说明）。
  收摊必须排在失败之前：收摊时伴生的失败只是「没跑完」的副产物，报成「同步完成（有
  失败）」会让人误以为整轮跑完了。
- 五组任务列表（进行中 / 待处理 / 已完成 / 已跳过 / 失败）**全量展示不折叠**——面板
  要一眼看全，折叠掉就等于把「哪些任务没跑完」藏起来。
- 阶段行与批次历史行**整行用 `<code>` 包裹**：计数列在各行间竖向对齐，代价是行宽变长
  （手机上可能折行）。这是面板特有的取舍，其它通知不要这样用，行内机器值仍按规范 · 机器值
  局部等宽。
- 时长只从收尾区出。

```
⏸️ 同步轮次收摊
━━━━━━━━━━━━━━━━━━
状态：待处理 4 · 进行中未执行完 2 · 失败 1
📊 总 12 · 待处理 4 · 进行中 2 · 完成 5 · 跳过 0 · 失败 1

时间预算到站，剩余任务下轮自动接力

🔄 进行中 · 2
  ├─ <code>onedrive:media/电影</code> · 3.1 GiB / 12 文件
  └─ <code>onedrive:media/剧集</code> · 800 MiB / 5 文件

run 已结束，以上任务本轮未执行完

⏳ 待处理 · 4
  └─ <code>onedrive:backup</code> · 1.2 TiB / 3200 文件

❌ 失败 · 1
  └─ <code>onedrive:music</code> · 源端读取被拒

⏱ 已运行 45 分钟 · 🔗 运行日志
```

面板是**唯一需要 message_id 的场景**（原地刷新 = 删旧 + 发新），因此也是唯一允许绕过
发送层直连 API 的地方；并发刷新要用锁串行化，否则会产生孤儿面板消息。

### 3.8 带动作行的通知

正文与动作行（超链接）之间要补一个空行，且**先判断正文是否已有尾换行**，避免产出双
空行：

```
⏳ 起播等待 · 4
  ├─ 你 → Cloudflare → Emby（预估值）：27 毫秒
  └─ 你 → OneDrive 拉流缓冲 · 这段服务器测不到

▶ 打开直链

⏱ 已运行 38 分钟 · 🔗 运行日志
```

### 3.9 媒体 caption

随视频发出的 caption：**没有标题、分隔线、收尾区**（收尾区唯一固有例外），拼完即随
媒体发出。三行依次为文件名 / 大小 / 修改时间（东八区）：

```
video_2026.mp4
1.150 GiB
2026-09-10 08:12
```

分片场景（超过 2000 MiB）中间行换分片信息，仍三行：

```
video_2026.mp4
part 2/3 (800MiB)
2026-09-10 08:12
```

它不走 sendMessage 发送层（媒体上传的固有例外），但同样**必须转义并显式 HTML
parse_mode**，否则文件名里的 `& < >` 会 400、markdown 语法字符会被 Telethon 默认
解析吃掉；429 重试与发送层同口径（最多 5 次）。

> 别与普通消息的标题前缀（如 `📺 ph` / `📺 91`）搞混——那是走发送层的文本通知。

## 4. 表达约定

### 4.1 时长

全库统一五层，按量级选：

| # | 形态 | 适用 | 示例 |
|---|---|---|---|
| 1 | `X 小时 Y 分`（分钟**不补零**） | ≥ 1 小时 | `2 小时 8 分`、`1 小时 0 分` |
| 2 | `X 分钟` | ≥ 1 分钟 | `20 分钟`、`45 分钟` |
| 3 | `X.XX 秒`（**两位小数**） | ≥ 1 秒 | `12.34 秒`、`59.00 秒` |
| 4 | `X 毫秒`（整数） | < 1 秒 | `27 毫秒`、`340 毫秒` |
| 5 | `⏱mm:ss`（定宽补零） | 进度面板批次行 | `⏱01:15` |

- 第 1–3 层由三套真源的收尾区实现，三者逐字一致；第 3/4 层的**正文单条耗时**
  （毫秒/秒双档，`27 毫秒` / `1.40 秒`）由 bash 真源 `tg_format_ms` 提供——
  emby 起播等待、openclaw 自愈告警的耗时 kv 都走它；python/pwsh 侧暂无消费场景、未实现；
- 正文需要**三段式时长**（如趋势通知的「历时」）时，bash 侧复用 `tg_format_duration`
  （与收尾区同源），python 用 `tg_format_elapsed`；不要自造新的同义实现（bash 里内嵌的
  python 段按规范 · 内嵌 python 段处理）；
- 第 3 层的两位小数是**固定精度**（整数秒写作 `12.00 秒`）：精度一致才好纵向比较；
- 第 4 层是子秒专用形态——不足 1 秒若硬走第 3 层会退化成 `0.00 秒`，所以单列一层；
- 第 5 层是**面板列字段**（为了计数列竖向对齐），与第 1–4 层不是一套体系；
- 修饰语前置、值里不重复标签语义：`约 15 分钟`（不是「预计…约 15 分钟后执行」）、
  `3 小时内`、`3 小时前`、`直链剩余 40 分钟`。
- 例外：测速节点指标串（`↑42兆 ↓58兆 35ms`）里的延迟用紧凑 `NNms`——它是指标字段，
  要和 `↑` / `↓` 等宽并排，不走第 4 层的「毫秒」写法。

### 4.2 大小

1024 进制 + 三位小数 + IEC 单位：`1.150 GiB`、`800 MiB`、`12.00 KiB`。
不要用 `du -h` 的 `1G` 口径，也不要输出裸字节（`1234567890 字节`）。

**通知口径 bash 侧只有一份实现**：通知真源 `tg_notify.sh` 的 `format_bytes`。凡是
source 了真源的通知点直接用它——openlist 域经 `load_all.sh` 注入，tg-channel 各脚本与
workflow 内联各自 source 真源。openlist 域另有 `format_bytes_iec`（`numfmt` 口径）与
若干 workflow 内联 `numfmt`，**只进日志 / env，不进通知**——别把它们用于通知，也别
误当成第二套通知口径。

**python 侧**拿不到 bash 函数，有两份同口径 `human_size`（1024 进制 + IEC + 三位小数）：

- `sync_to_tg.sh` 内嵌 `human_size`：**唯一进入通知**的 python 侧实现，改口径必须跟着改；
- `add_uploaded_video.py` 的 `human_size`：只写 `uploaded_videos.json` 台账与日志，
  不进通知（同为 IEC 口径，改口径时一并改）。

`speedtest_common.py`（测速共享层）与 pwsh 侧都没有大小助手，需要时由调用方按同一口径
格式化。

### 4.3 日期与相对时间

`YYYY-MM-DD HH:MM（东八区）` + ` · N 小时前`（解析失败保留原值）：

```
时间：2026-09-07 19:34（东八区） · 3 小时前
```

不要直出 ISO 时间戳（`2026-09-05T11:34:19Z`），也不要写 UTC：**通知里的展示时间
一律东八区**（Asia/Shanghai），由 `TZ=Asia/Shanghai date …` / `tg_format_time_bj`
换算。机器值（marker / JSON / 日志 / run 时间戳）仍按 UTC 存，两者不要混用。

### 4.4 计数与量化

- 分节计数：`{emoji} 分节 · N`。
- 影响写进 kv 的计数与量化：失败 3 个 / 减少 100 GiB / 跳过 12 条。
- 错误码中文化：`退出码 45` 而不是 `exit=45`。
- 文件数行：`源端 X / 目标 Y` 恒定；**源端比目标端多**时前置 `差异 N · `（N>0）。
  目标端更多时不要前置——那会渲染出负数的「差异 -1」（上一轮修复留下的替代名、
  删除未执行都会造成），读者看不懂。两端一致时写 `X · 一致`。
- 面板批次行定宽：`✅00 🔧00 ❗33 ⏭️22 ♻️22 ⏱01:15 ⬆️4.79G`——五个计数补零，
  上传量取 GiB 两位小数，最近 6 条滚动。

### 4.5 状态图标语义

| 图标 | 语义 |
|---|---|
| `✅` | 成功 / 恢复边沿 |
| `🟢` | 服务就绪（网关 / runner 入口类通知的主标题图标） |
| `⚠️` | 部分失败 / 警告 / 降级但可用 |
| `❌` | 失败 |
| `🔴` | 需人工解封（上游风控停用账号池） |
| `🟠` | 需人工介入（介于警告与失败之间） |
| `🟡` | 降级但服务在（通道缺失 / 额度耗尽——等即可，不用动手） |
| `⛔` | 中断（注册前即死） |
| `⏸️` | 轮次收摊（预算到站，预期内）——**只用于**同步面板终态标题 |
| `⏭️` | 跳过 |
| `⏳` | 待处理 |
| `🔄` | 进行中 / 接力启动 |
| `🚨` | 危险警告 |
| `🆘` | 灾难恢复 |
| `📍` | 进度面板当前阶段 |
| `🚫` | 本轮中止（预期内收尾而非故障，如配额预检不通过） |
| `🧯` | 自动接力熔断（保活链路停摆，需手动 dispatch 恢复） |
| `🧹` | 清理类（残留文件清理、频道清理） |
| `🕒` | 报告时刻（**只用于**无 run 上下文的常驻服务收尾区，不与其他场景混用） |

建议图标与结论一致，不要自造 `⭐` / `🥇` 之类前缀。同一条通知里避免两个相同 emoji
承担不同角色（如两个 `📍`）。

### 4.6 常见偏差与改进建议

| 偏差 | 为什么会这样 | 建议改成 |
|---|---|---|
| 手拼 HTML（`msg+="<code>…"`） | pwsh 无助手；bash/python 已全部走助手 | 用规范 · 助手速查的助手（pwsh 按规范 · 版式构件形态手拼、值经 `Esc-Html`） |
| 分节后跟列表却没计数 | 忘了拼 | 带 ` · N`：`❌ 失败清单 · 3` |
| 条目用 `• ` 平铺 | 沿用了平铺写法 | 改 `├─/└─` 树形 |
| 长列表全量穷举（流水类） | 怕漏信息 | 分组 + 每组 8 条 + 折叠行；结构性清单不折叠 |
| 英文紧凑时长（`5h 57m`） | 脚本内部格式直接输出 | 中文分层（规范 · 时长）：`⏱ 已运行 5 小时 57 分` |
| 高精度浮点（`2.16068914 秒`） | 原始值直出 | 两位小数：`起播 2.16 秒` |
| ISO 时间戳直出 | 原始值直出 | 东八区 + 相对时间 |
| 半角冒号 kv（`状态: 成功`） | 手误 | 全角冒号：`状态：成功` |
| 手拼收尾行 | 不知道有助手 | 一律 `tg_add_footer` / `Get-TgFooter` / `tg_footer_line` |
| 已引入发送层仍 curl 直发 | 想要 message_id 等 | 除进度面板外一律走发送层：`send_tg "$msg"` |
| 失败原因写内部机制（熔断 / 探测 / 哈希目录） | 直接透出实现层的判据变量 | 翻成人话（规范 · 说人话），细节留日志 |
| 把运行日志搬进通知当条目子行 | 想省一次点链接 | 子行只补一句话，过程走运行日志链接 |
| 子行前缀比条目前缀宽一格（6 vs 5 字符） | `tree_sub` 比 `tree_conn` 多写一个空格 | 两者定宽必须相等（规范 · 条目与树形） |
| 树形前缀裸文本发送（不包 `<code>`） | 以为等宽对齐理所当然 | 前缀包进 `<code>`，竖线严格成列 |
| 单独列 rclone 差异清单（新增 / 仅目标存在 / 不一致） | 想交代「还差多少」 | 不列：与失败清单、已修复清单重复，且把已处理的也算进差异。规模由文件数行交代 |
| 函数体内 `source` 真源 | 以为可重复 source、想每个调用点自带一份 | 只在顶层/step 顶层 source 一次（规范 · 通知函数的正确接法） |
| 长跑接力轮重复推同一条通知 | 新 run 是上一轮接力启动，服务与账号池没变，却又跑一遍同样的判断 | 用 `/tmp` 下的标记文件区分首轮与接力轮，接力轮只记日志不发通知（规范 · 通知函数的正确接法） |

## 5. 实现与接线

### 5.1 选哪套

| 场景 | 用哪套 | 有什么 / 没什么 |
|---|---|---|
| Linux / macOS runner 的 bash step | `.github/scripts/telegram/tg_notify.sh` | 助手最全：排版、条目、树形、折叠、收尾、日志截断、发送（含分片）都有 |
| Windows runner（pwsh） | `.github/scripts/telegram/tg_notify.ps1` | **只有** `Esc-Html` / `Format-TgDuration` / `Get-TgFooter` / `Send-TgMessage` / `$TG_SEP`——没有 kv 与条目助手，全部手拼，也没有分片发送 |
| python 脚本 | `.github/scripts/proxy-speedtest/speedtest_common.py` | 有条目与收尾的镜像函数（返回字符串，需自己 `join`）、发送与分片（`send_telegram` / `send_telegram_chunked`，支持 tier）、`TG_SEP` 与时间换算；**没有** `tg_add_*` 变量累积机制、没有大小助手 |
| bash 里内嵌的 python 段 | 无法 import 共享层 | 必须在本文件内同义实现用到的助手（规范 · 内嵌 python 段） |

### 5.2 接线（硬要求）

每个发通知的 step 都需要：

```yaml
      - name: "Notify: xxx 结果"
        if: ${{ always() }}
        env:
          TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
          # 重要档通知（send_tg "$msg" alert = 告警 + 信息）的 step 才需要注入以下两行：
          TELEGRAM_BOT_TOKEN_ALERT: ${{ secrets.TELEGRAM_BOT_TOKEN_ALERT }}
          TELEGRAM_CHAT_ID_ALERT: ${{ secrets.TELEGRAM_CHAT_ID_ALERT }}
          TG_RUN_URL: https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

- **只有 `TG_RUN_URL` 需要注入**；`TG_RUN_STARTED_AT` 不要注入（平台无此上下文、恒为
  空串），助手侧走 `/proc/1` 兜底。
- 凭据校验在**调用方**，且放在引入真源**之前**：`if [ -z "$TELEGRAM_BOT_TOKEN" ] …exit 0`。
  真源本身不校验。注意这只适用于「整个 step 没凭据就什么都不该发」的场景；
  **alert 档凭据缺失时不要加静默守卫**——发送层的「缺失即失败留痕」是故意的
  （规范 · 发送层要求），提前 `if` 掉会把告警静默吞掉。
- **重要档两档分类**：`send_tg "$msg" alert` / `send_tg_chunked "$msg" alert` /
  `send_telegram_message "$msg" HTML alert` 的 step 还需注入
  `TELEGRAM_BOT_TOKEN_ALERT` / `TELEGRAM_CHAT_ID_ALERT`；`alert` 档直达、不回退主
  bot——凭据缺失时发送失败并在日志留痕。档位由调用点显式声明，发送层不按标题匹配。
  **重要档 = 告警 + 信息**：告警（备份失败/归档告警/网关启动失败/源端异常/灾难恢复/
  Pixiv cookie 失效）＋ 信息（入口/凭据/模型倍率/服务启停/各网关已就绪）。
  `⛔ 同步中断`（未注册任何任务）是**进度面板终态**，面板直连 API 恒主 bot、
  不参与档位路由——结构上到不了 alert，别按此清单给它接 ALERT 凭据。
  其余（结果 + 流水）为**普通档**，不传 tier。
- bash 真源兼容历史变量名 `TG_BOT_TOKEN` / `TG_CHAT_ID`；**pwsh 侧没有这层回退**，
  必须注入 `TELEGRAM_*`。
- python 侧凭据从传入的 `env` 读（`send_telegram(env, text, tier)` 的 alert 档读
  `TELEGRAM_BOT_TOKEN_ALERT` / `TELEGRAM_CHAT_ID_ALERT`），但 `TG_RUN_URL` 只读
  `os.environ`，只给 dict 不够。
- pwsh 的 step 要 `shell: pwsh`；引入真源后建议加 `Get-Command Send-TgMessage` 自检——
  调用未定义函数是终止错误，step 带 `continue-on-error` 时会表现为通知静默消失。

### 5.4 内嵌 python 段

bash 里内嵌的 python 段（`python3 - <<'PY'`）无法 import 共享层，用到的助手必须在本
文件内同义实现，且与共享层逐字一致。**新增助手时别忘了同步补进内嵌段**——否则会出现
`NameError` → python 非零退出 → 脚本提前退出 → 连整轮汇总通知一起丢。这类问题代码
审查很容易漏（函数名看着就像内置的），改完务必实跑一次。

### 5.5 通知函数的正确接法（子 shell 陷阱与接力轮去重）

**真源只在顶层 source 一次。** 真源的函数定义**重复执行不会报错**（bash 允许
同名函数重复定义、后定义覆盖前定义），但这只保证「不会 source 崩掉」，
**不代表在函数体内 source 等价**。函数体往往在**子 shell**
里执行——`m=$(fn)`、`fn | …`、`fn &` 都会 fork：

- 子 shell 内 `source` 只改子 shell 的函数表，**父 shell 里调用点做的覆写不会被还原**
  （反过来也成立：子 shell 里的覆写出了子 shell 就没了）；
- 子 shell 里 `local` 只对**子 shell 的调用栈**有意义，父 shell 看到的是全局变量——
  「函数内 `local` 就不会污染全局」在这类函数里不成立。

这两条合起来会产出非常难查的 bug：调用点 `send_tg() { … }` 想拦下发送做本地预览，
函数体内再 source 一次真源，定义就被**还原成真发**，于是预览脚本真的往 Telegram 发了消息，
而且 `$( )` 把 stderr 也吞掉，只看得到一句「发送失败」。正确写法是：

```bash
source "${GITHUB_WORKSPACE}/.github/scripts/telegram/tg_notify.sh"   # step 顶层，一次

wb_notify() {                    # 函数体只用助手，不再 source
  local _msg=""
  tg_add_title _msg "$1"
  …
  send_tg "$_msg" || echo "::warning::TG 通知发送失败（不影响任务）"
}

wb_notify …                      # 顶层调用；要改行为就在顶层覆写 send_tg
```

**同一份 service 由接力 run 反复启动时，同一条通知只推一次。** 长跑 workflow 收尾时用
`gh workflow run …` 接力启动新 run，新 run 会把同一套启动逻辑原样再跑一遍——同一个服务、
同一份账号池，通知内容与上一条完全相同，只是把消息列表刷屏。判据放在 `/tmp` 下的标记文件
（runner 生命周期内有效，每个 run 一台新 runner）：

```bash
TAG_FILE="/tmp/workbuddy-serve-run-tag"
RELAUNCH=0
if [ -s "$TAG_FILE" ]; then RELAUNCH=1; fi        # 文件在 → 上一轮已启动过 = 接力轮
if [ "$READY" = "1" ]; then
  printf '%s\n' "${GITHUB_RUN_ID:-manual}" > "$TAG_FILE"
  if [ "$RELAUNCH" = "1" ]; then
    echo "ℹ️ 接力轮（上一 run ${PREV_TAG} 已启动），跳过重复的就绪通知"
  else
    send_readiness_notify
  fi
fi
```

标记文件**只在服务真的起来时写**：启动失败的回退/重试路径不会被记成「已启动」。
文件被 runner 回收后探测自然归零，按首轮处理——多发一条好过漏发。

## 6. 发送层要求（硬约束）

- **一律 HTML parse_mode**，动态内容**必须**转义（`escape_html` / `Esc-Html` /
  `html.escape`，或经 `tg_*` 助手自动转义）。没有「值是脚本自造、字符集受限」的豁免。
- **HTML 解析失败（400 can't parse entities）不重发**，直接报错暴露并带上响应体前
  200 字符：消息本来就没发出去，退化成纯文本只会把 bug 藏起来。
- **429 限流按 `retry_after` 等待重试（最多 5 次尝试）**；长消息自动分片，断在换行
  处、不切 UTF-8 多字节。分片口径**三套实现有意不同**，各按自己的上限执行即可：
  - bash 真源（`send_tg` / `send_tg_chunked`）：>3900 UTF-16 码元触发分片，按
    **3800 UTF-16 码元**切——Telegram 上限按 UTF-16 码元计，Python 字符数会低估
    emoji 等增补平面字符；并在分片边界**自动闭合/重开 HTML 标签**（`<pre>`/`<code>`
    不会被切断）。5xx / 网络错误也做退避重试。
  - python 共享层（`send_telegram_chunked`）：按 **4000 Python 码点**切，**无**标签
    闭合——超长 `<pre>` 会在边界破版，故原始输出按尾部 1200 字节截断（规范 · 多行块）。
  - pwsh：无分片实现（见本章末「已知差异」）。
- 发送失败**必须**在 stderr / 日志输出原因（含响应体前 200 字符），由调用方决定
  `|| true` 还是失败；**不要 `>/dev/null 2>&1` 吞掉**。python 侧 `send_telegram` 返回
  字典（失败带 `reason`；唯一例外是 429 重试耗尽抛异常，见「已知差异」），调用方
  **必须**把原因记进日志。
- **已引入发送层的通知点不得 curl 直发**。唯一例外是需要 message_id 的进度面板原地
  维护（规范 · 进度面板），以及媒体上传的 `sendDocument` / `sendVideo`（caption
  同样必须转义，429 重试与发送层同口径）。
- **档位路由（两档）**：`send_tg` / `send_tg_chunked` 收可选 `tier`（pwsh
  `Send-TgMessage <text> [tier]`，python `send_telegram(env, text, tier)`）。只有两档：
  - `alert` = **重要通知**（告警 + 信息）→ @SaberFuckBot（secrets 已配置，无回落，
    凭据缺失即失败留痕）；
  - 不传 tier = **普通通知**（结果 + 流水）→ @FuckSaberBot。
  进度面板直连 API 固定主 bot，不参与路由。
  测速三套的主报告走普通档，❌/⛔ 异常兜底走 alert 档（`notify_best_effort` /
  未捕获 handler 显式传 `'alert'`）；对应 workflow 已注入 `_ALERT` 凭据。

### 6.1 全库 bot 分工（唯一口径）

> 改任何通知路由前先对照这里，避免把业务通知与内部消息混用。

| bot | 职责 | 本机 | 仓库 |
| --- | --- | --- | --- |
| @openclaw_sb_bot | 主对话（与人对话，不发通知） | ✓ | — |
| @FuckSaberBot | **一般通知**（业务） | ✓ | ✓ |

| @sbsb / @sbsbsb / @sbsbsbsb / @sbsbsbsbsb | agent 各自对话窗口 | ✓ | — |
| @ass_openclaw_bot | **内部消息隔离带**（relay / 后台完成 / 串号排查） | ✓ | — |

**两档 × 两侧，共 4 格，只用 2 个通知 bot**：

| | 本机 | 仓库 |
| --- | --- | --- |
| **一般通知** | @FuckSaberBot | @FuckSaberBot |
| **重要通知** | @SaberFuckBot | @SaberFuckBot |

**判定口径**

| 档位 | 承载内容 | 判定 |
| --- | --- | --- |
| 一般 | 业务类：`send_tg` 不传 tier（备份结果、同步状态、测速结果等） | 默认路径 |
| 重要 | runner 重启、setup-env 报告、测速告警、`tier=alert` 告警档 | 显式传 `alert` |

> **内部消息不属于上面任何一档。** exec completion relay、心跳残留、卡死会话恢复等

> 判据：业务一般通知是「人该看到的业务结果」，内部消息是「没人主动问的系统流水」，
> 两者不能共用一个 bot。

> ⚠️ **判据（易踩）**：GitHub Secrets 只写不可读，本机 `.env` 的值 ≠ 仓库 secrets 的值。
> 判断「仓库接的是哪个 bot」**只能靠消息头**（转发任意一条通知即可看到发送 bot 的
> 显示名 + username），拿本机 token 去推断仓库必错。

> ⚠️ **不要**把本机裸变量 `TELEGRAM_BOT_TOKEN` 改值——它是本机重要通知（runner 重启、
> setup-env 报告、测速告警）的出口，改了会直接切断重要告警通道。

已知差异（不是规范，是现状，修完可删）：

- pwsh 侧无分片实现，超长消息会被 Telegram 直接拒。
- python 侧 429 耗尽路径是抛异常而非返回字典。
- python 侧分片按 4000 Python 码点、无 HTML 标签闭合，与 bash 的 3800 UTF-16 码元 +
  标签闭合不同口径（见本章分片条目）；统一口径时以 bash 为准。

### 7.2 回归套件

改到 openlist 域的脚本时跑回归（`.github/scripts/openlist/tests/` 下的套件）：

```bash
cd .github/scripts/openlist/tests
for t in test_*.sh; do bash "$t" </dev/null > "/tmp/x_${t%.sh}.log" 2>&1; echo "$t EXIT=$?"; done
grep "command not found" /tmp/x_*.log
```

- 必须重定向 stdin，否则个别套件会卡在读 stdin。
- **套件 PASS 不等于通过**：跑完必须 grep `command not found`，**必须为空**——函数没
  被引进来时测试可能照样 PASS。
- 具体基线（各套件的预期结果与已知环境失败）见
  `skills/telegram-notify-audit/references/audit-checklist.md`，那边会随实现更新，
  这份文档不再复制一份数字。
- 几个依赖本机环境的套件：需要 docker 或真实服务的、用到 GNU `date -d` 的（macOS 的
  BSD `date` 没有 `-d`）、以及时序敏感的。跑出来与基线不符时先单独复跑确认，别急着
  改代码。

## 8. 术语

- **面板**：需要 message_id 的原地刷新消息（openlist 进度面板）。
- **结构性清单**：读者要逐条核对、折叠掉会造成误判的清单（与流水类相对）。
- **硬约束**：不遵守会造成通知丢失或误判失败的规则（规范 · 收尾区、规范 · 接线、
  规范 · 发送层要求、规范 · 验证与交付）。
