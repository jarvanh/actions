# Telegram 通知规范（全库唯一真源）

全库所有 Telegram 通知——workflows 内联的、scripts 下各子系统的——都在这里找答案。

**这是风格指南，不是军规。** 绝大多数条目是「建议 + 为什么 + 反例」，目的是让你在没有
先例可循时也能写出和别人风格一致的通知。只有第 7 章发送层、3.9 收尾区与接线、第 8 章
回归基线这三处是硬约束，不遵守会造成通知丢失或误判失败。

改动流程：版式改动**先改这份文档，再同步实现**；实现改完跑一遍渲染预览（8.1 节）。

配套 skill（在仓库根 `skills/` 下）：写新通知用 `telegram-notify-send`，
核对全库版式用 `telegram-notify-audit`。

**引用本规范时写「规范 · 主题名」**（如「规范 · 折叠规则」「规范 · 取值行口径」），
不要写章节号——章节号会随文档重排变化，主题名不会。

## 1. 设计原则

### 1.1 一条通知要回答三个问题

> **发生了什么 / 影响多大 / 我要做什么**

写通知前先过一遍这三问，比纠结用哪个 emoji 更有价值：

- 发生了什么 → 标题（emoji + 短语）+ 状态 kv
- 影响多大 → 计数与量化（失败 3 个 / 减少 100 GiB / 跳过 12 条）
- 我要做什么 → 复制即用命令块、下一步说明、运行日志链接

### 1.2 视觉层级靠三件套

| 手段 | 承担的作用 |
|---|---|
| 分隔线（18 条全角横线 `━`） | 标题锚点 |
| 空行 | 段落与分节的边界（只有固定几处产生，见 3.10） |
| emoji | 语义与状态的彩色锚点 |
| 等宽 `<code>` | 「这段可以直接复制」的机器值 |

建议不用 `<b>` 与 `<i>`：上面三件套已经给足了区分度，而且省掉「哪里该加粗」的判断
成本（条目主体和 kv 值的边界很难说清）；另外 `<i>` 对中文几乎看不出效果，只会让
HTML 变复杂。

### 1.3 只有三种标签

| 标签 | 用在哪 |
|---|---|
| `<code>` | 机器值：路径、文件名、命令、密码、IP、ID、端口、原始异常串 |
| `<pre>` | 多行块：日志、复制即用命令、异常栈（保留换行、整块复制） |
| `<a>` | 链接：收尾区运行日志、订阅源、播放直链 |

其余一律裸文本——但动态内容要**转义**（`& < >` 会触发 400，见第 7 章）。

**取值行口径**：一条取值行（`标签：值`）用等宽还是裸文本，只看一件事——**它是不是
机器返回的值**。

| 值的性质 | 口径 | 例 |
|---|---|---|
| 机器返回（IP、ISP、ASN、位置、主机名、域名、版本、ID、端口、路径、文件名、命令、原始异常串） | `<code>` | `位置：<code>Tokyo, JP</code>` |
| 自然语言（原因、状态描述、结论、备注） | 裸文本 | `状态：部分失败` |

判据取「来源」而不是「值值不值得复制」：一次归属查询返回的 IP / ISP / ASN / 位置
同属一批机器返回值，建议整节同为等宽；若按「ISP 和位置没人会去复制」逐个判断，
同一节就会变成「IP 等宽 → ISP 正体 → ASN 等宽 → 位置正体」的斑马纹，读者只会
理解成版式出了 bug。计数、时长、状态这类人写的结论值本来就裸文本，不受这条影响。

### 1.4 统一优先于个性

同一类信息在不同子系统里形态一致，读者才能跨通知扫读。因此版式尽量走真源助手
（6.3 节），而不是各脚本自己拼字符串。

### 1.5 说人话，术语留日志

通知的读者不一定是实现者。**凡是读者要「看懂」的字段，一律用日常说法**——失败原因、
状态、结论、说明段都属于这一类：

| 别写（内部机制） | 写成（人话） |
|---|---|
| 后端写熔断，未探测 | 存储端本轮整体故障，未试写 |
| 已重启容器复核 | 已复核确认 |
| 短哈希目录 / base64URL 目录 | 备用目录 / 编码目录 |
| 目标目录不可写（原目录与短哈希目录均未通过可写性预检） | 目标目录不可写（存储端本轮整体故障，未试写；无目录可换） |

判据是「**这句话是给实现者排查用，还是给读者做判断用**」：排查用的细节（`rc=1`、
`HTTP_CODE:200`、缓存口径、容器重启、方法名与黑名单）全部留在运行日志里，通知只给
结论与下一步。把日志原样搬进通知（尤其是搬成条目子行）会把一条通知撑成几十行，
同时把结论埋在中间——这是最难看的形态。

术语不是不能出现，是要**有边界**：`<code>` 里的路径、命令、原始异常串照旧原样输出
（1.3 节），那是可复制可搜索的机器值；被翻译的只有「需要读者理解」的自然语言字段。

## 2. 通知种类速览

全库通知按子系统分组列在下表，「在哪」只给文件——具体行号会随实现漂移，用函数名
或标题文案去搜更快。其后是**代表性渲染示例**，写同类通知时照着这个形态来。

### 2.5 告警与异常兜底

| 通知 | 在哪 | 何时发 |
|---|---|---|
| 🚨 OpenClaw 自愈失败 | `openclaw.yml` | 主步骤失败，推失败阶段 / 版本 / 关键日志 |
| ⚠️ OpenClaw 归档告警 | `openclaw.yml` | 周期归档失败（rclone/tar） |
| ⚠️ OpenClaw 最终归档告警 | `openclaw.yml` | 最终归档失败（标题带「最终」区分阶段） |
| ✅ OpenClaw 最终归档结果 | `openclaw.yml` | 最终归档收尾，按对象汇总结果（有失败 / 全失败降级 ⚠️ / ❌） |
| ⚠️ OpenClaw 即将进入最终归档 | `openclaw.yml` | keepalive 剩余约 15 分钟时预警 |
| ⚠️ Emby 直链已回退 | `emby.yml` | 探活连续失败切直连 |

**示例：归档告警**

```
⚠️ OpenClaw 归档告警
━━━━━━━━━━━━━━━━━━
对象：<code>openclaw.tar.gz</code>
结论：上传失败 · 退出码 2
原因：rclone 上传失败
Run ID：<code>12345678</code>

🧾 原始输出
<pre>2026/09/12 09:00:00 ERROR : Failed to copy: connection reset</pre>

⏱ 已运行 41 分钟 · 🔗 运行日志
```

周期归档与最终归档的两个告警函数分处不同 step、定义无法共享，**改版式时两处要一起改**；
二者标题需区分，否则读者分不清告警来自哪一轮。

**示例：最终归档结果**

```
✅ OpenClaw 最终归档完成
━━━━━━━━━━━━━━━━━━
结果：成功 4
大小：合计 1.140 GiB
快照：<code>openclaw-20260912-1330-v1.2.3.tar.gz</code>

📦 归档明细 · 4
  ├─ <code>openclaw.tar.gz</code> · ✅ 28.000 MiB · 覆盖主包
  ├─ <code>zcode.tar.gz</code> · ✅ 12.000 MiB
  ├─ <code>CliRelay.tar.gz</code> · ✅ 1.100 GiB
  └─ <code>rsstt.tar.gz</code> · ⏭️ 跳过 · 本轮未产生数据

⏱ 已运行 5 小时 46 分 · 🔗 运行日志
```

- 明细是**固定几项的结构性清单**（最多 5 项），全量展示不折叠——折掉任何一项都会让
  读者误判归档是否完整。
- 快照是主包的副本，单列一行、**不并入明细与合计**（否则与主包重复计数）。
- 计数只列非零项（`成功 4` 而不是 `成功 4 · 失败 0 · 跳过 0`）；全部失败时 `大小` 整行跳过。
- 归档步骤没产出明细（预检 `exit 1` / 运行被取消）时降级为 `⚠️ … 最终归档未完成`，
  这类失败在归档步骤内不产生任何通知，全靠这条兜底。

### 2.8 媒体 caption（特殊形态）

随视频发出的 caption，**没有标题、没有分隔线、没有收尾区**——它是 3.9 收尾区唯一的
固有例外，拼完即随媒体发出：

```
video_2026.mp4
1.150 GiB
2026-09-10 08:12
```

分片场景（超过 2000 MiB）中间行换成分片信息，**仍为三行**：

```
video_2026.mp4
part 2/3 (800MiB)
2026-09-10 08:12
```

它不走 sendMessage 发送层（媒体上传的固有例外），但同样**必须转义并显式 HTML
parse_mode**，否则文件名里的 `& < >` 会 400、markdown 语法字符会被 Telethon 默认解析
吃掉；429 重试与发送层同口径（最多 5 次）。

> 别把两种「caption」搞混：2.2 节频道同步汇总里的 `CAPTION_PREFIX` 是**普通消息**，
> 走 `tg_add_title` + 发送层；本节说的才是随媒体发出的 caption。

### 2.9 没有通知的 workflow

`subs-check.yml` 等一批 workflow 当前不发通知。要补的话，照 2.3 节备份类的形态即可
（标题 + 关键 kv + 收尾区），并把 `TG_RUN_*` 接上（3.9 节）。

## 3. 版式构件

每个构件给出：形态 → 用处 → 助手 → 建议与反例。助手的跨语言对照见 7.3 节。

### 3.1 标题与分隔线

```
{emoji} 标题
━━━━━━━━━━━━━━━━━━
```

- 助手：`tg_add_title`（bash）；pwsh / python 用 `TG_SEP` 手拼。
- 建议：emoji + 短语，状态与细节下沉到 kv 行；标题后紧跟分隔线、不空行。
- 分隔线恒为 18 条全角横线，四套实现同值，不要自造。

### 3.2 kv 行

```
标签：值
```

- 助手：`tg_add_kv`（值自动转义，裸文本）。
- 建议：全角冒号；多个字段用 ` · ` 连接。
- 一行塞多个字段时，用全角冒号标签打头作锚点（`规格：` / `链路：` / `客户端：`），
  避免无锚点的裸 ` · ` 串。

### 3.3 机器值

```
路径：<code>/mnt/media/a.mp4</code>
```

- 助手：`tg_add_path`。
- 建议：路径 / 文件名 / 命令 / 密码 / IP / ID / 端口 / 原始异常串一律等宽——读者一眼
  看出「这段可以直接复制」。判据见 1.3 节。

### 3.4 分节

```
{emoji} 分节 · N
```

- 助手：`tg_add_section`（段前自动空行；紧跟分隔线时自动不空行）。
- 建议：**分节后跟条目列表时带计数 ` · N`**（规模一眼可见）；后面是 kv 行或单段说明
  时可以不带。
- 反例：`❌ 失败清单`（后面是 3 条条目却没有计数）。

### 3.5 条目与树形

```
  ├─ <code>video_a.mp4</code> · 1.7 GB · 2160p
  └─ <code>video_b.mp4</code> · 重试修复失败
```

- 助手：`tg_entry`（单行）/ `tg_add_entry`（累积多行）；双机器值用 `tg_entry_pair`
  （`→` 替换关系）或 `tg_entry_codes`（`·` 并列）；与 `tree_lines` 组合成树形条目流。
- 建议：条目一律 `├─/└─` 树形；元数据用 ` · ` 分隔、放在主体之后。
- 注意：`$(tg_entry …)` 不输出尾换行，命令替换还会吃掉它，**累积多行请用
  `tg_add_entry`**——否则条目会粘成一坨。
- 反例：`• video_a.mp4` 平铺。

### 3.6 折叠行

```
  └─ 还有 8 条…
```

- 助手有两个，按**输入是裸文本还是已构建条目流**选，选错会造成二次转义：

  | 助手 | 输入 | 做什么 |
  |---|---|---|
  | `tree_code_fold` | 裸文本（未转义、无标签） | 逐行转义 + 套 `<code>` + 超上限折叠 |
  | `tree_fold` | 已由 `tg_add_entry` / `tg_entry` 构建的条目流 | **只**截断 + 加折叠行 |

  对已含 `<code>` 的条目流误用 `tree_code_fold`，会把 `&` 转成 `&amp;amp;`、并把
  `<code>` 本身转义掉。
- 建议：折叠行并入条目流作末条（由 `tree_lines` 统一决定 `└─`），不要单独补一行造成
  双 `└─`。

**折叠与否看清单性质，不只看条数**：

| 清单性质 | 超上限怎么办 | 例 |
|---|---|---|
| 流水 / 日志类（读者只需知道规模，单条价值低） | 折叠为「还有 N 条…」 | 已上传文件、删除的重复文件、排除规则、日志行 |
| 结构性清单（读者要逐条核对，少一条就漏了结论） | **全量展示，不折叠** | 任务预览的同步对、进度面板的五组任务列表、批次统计清单 |

判据是「折叠掉后半段会不会让读者误判」，不是「列表长不长」。结构性清单若确实很长，
靠分节计数 ` · N` 交代规模即可——把「失败了哪些」折叠成「还有 N 条…」，等于把读者最
需要看的部分藏起来。

**二层列表（条目 + 子行）不在 `tree_fold` 适用范围内**：`tree_fold` 按「行」截断，而
带子行的列表截断单位是「条目」（1 条目行 + N 行子行），按行截断会把子行切在半路。这类
列表由调用方按条目计数并自行补折叠行（用 `tree_sub` 缩进），折叠行仍并入条目流作末条。
实例见任务预览的条目子行（`差异构成：` / `排除 · N`）与去重通知的方法摘要。

**子行是给一个条目补一句话，不是给日志开口子**：往子行里灌原始日志，单文件就能撑出
十几行（源/目标全路径、rclone 原始报错、内部机制术语），是通知里最难看的形态，而且
结论会被埋进噪音里。失败原因写进条目行的元数据、一句人话说完（规范 · 说人话），
要看过程的读者走收尾区的运行日志链接——同步结果通知的失败清单曾是这种反例，
2026-09-12 删掉子行后回到单行条目流。

### 3.7 多行块（日志 / 命令）

```
<pre>gh workflow run openlist.yml -f run_mode=同步</pre>
```

- 助手：`tg_add_pre`（转义 + `<pre>` 包裹）；`tg_add_block` 只用于已含标签的片段。
- 建议：日志、异常栈、复制即用命令用 `<pre>`（保留换行、整块复制）；不要用它替代行内
  `<code>`。
- 原始输出建议取**尾部 1200 字节**：超长输出会让 `<pre>` 跨 4000 字符分片，标签断开
  即破版。

### 3.8 说明段

```
如确认无误，请手动触发 force_sync=true
```

- 助手：`tg_add_note`（段前自动空行）。
- 建议：说明、备注、免责声明用独立说明段，与数据区分开。注意该助手对整段转义，
  **段内不能携带 HTML 标签**。

### 3.9 收尾区（硬要求）

```
⏱ 已运行 22 分钟 · 🔗 <a href="…">运行日志</a>
```

**硬要求**：所有通知都要有收尾区，唯一例外是媒体 caption（2.8 节）。进度面板每次刷新
都带收尾区，时长只从这里出。

必须用 `tg_add_footer` / `Get-TgFooter` / `tg_footer_line`，不要手拼——助手已处理空行、
降级与链接。附加链接可用 `tg_add_footer <var> "标签" "URL"` 追加多个 `· 🔗 <a>`。

- 语义是 **run 已运行时长**，不是步骤自身耗时；格式见 5.1 节的时长五层。
- 降级链：`TG_RUN_STARTED_AT` → runner 开机时刻 → 不显示时长；`TG_RUN_URL` 缺失则整行
  跳过。平台目前不注入 `TG_RUN_STARTED_AT` 的值，多数情况下走开机时刻兜底（误差秒级）。

**接线（硬要求）**：workflow 必须在 job 或 step 级 env 注入，否则通知没有日志入口：

```yaml
env:
  TG_RUN_URL: https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}
  TG_RUN_STARTED_AT: ${{ github.run_started_at }}
```

配合 `if: ${{ always() }}`——通知写在业务块末尾而没有 `always()`，任务失败时反而收不到
通知。

### 3.10 空行的来源

只有这几处会产生空行，其余地方建议不要手写 `\n\n`：

1. `tg_add_section` 段前
2. `tg_add_note` 段前
3. `tg_add_footer` 前
4. **正文与动作行之间**（如「▶ 打开直链」超链接），由调用方补——先判断正文是否已有尾
   换行，避免产出双空行
5. **多组列表的组与组之间**（任务预览的源端分组、去重通知的重复组）。这是唯一允许
   手写的空行，但**必须带条件**：只在前面已有组时才补。首组之前也补一次，分节标题与
   首组之间就会多出一个空行。

分隔线与紧随其后的内容之间不空行。

## 4. 常见模式与最佳实践

这一章是可直接套用的写法模板。第 2 章是「线上通知长什么样」，这一章是「你要写时
怎么搭」。

### 4.1 结果通知

建议顺序：**标题（状态 emoji）→ 关键 kv（对象 / 状态 / 计数）→ 明细分节 → 收尾区**。
状态与结论下沉到 kv，标题只说「谁 + 怎么了」。

多分支时**共用一条收尾与发送出口**，不要每个分支各发一次：

```bash
case "$STATUS" in
  cancelled) tg_add_title msg "⛔ 任务已中断"
             tg_add_note  msg "任务被取消，数据未受影响；如需继续请重新运行。"
             tg_add_footer msg; send_tg "$msg"; exit 0 ;;   # 提前返回，避免二次追加
  success)   tg_add_title msg "✅ 备份成功"; tg_add_kv msg "状态" "完成" ;;
  *)         tg_add_title msg "❌ 备份失败"; tg_add_kv msg "状态" "失败" ;;
esac
tg_add_footer msg
send_tg "$msg" || echo "::warning::TG 通知发送失败（不影响任务）"
```

```
✅ 备份成功
━━━━━━━━━━━━━━━━━━
日期：2026-09-10
文件：<code>backup.tar.gz</code>
大小：1.150 GiB
状态：完成

⏱ 已运行 18 分钟 · 🔗 运行日志
```

要点：

- 状态图标随结论降级——0 成功、数据缺失、中止，都该降为 ⚠️ / ❌，不要恒 ✅。
- 降级依据是**本轮发生的事**，不是库存里的历史累计数：拿累计数判定会让通知永久标黄，
  读者分不清「这轮出事」还是「旧账没清」。累计数放 kv 并标注「（累计）」。
  （ph-dl 收尾曾按累计损坏数降级，导致 0 下载的空转轮次也报 ⚠️。）
- 发送失败用 `|| echo "::warning::…"` 或 `|| true` 留痕，**不要** `>/dev/null` 吞掉（第 7 章）。
- 步骤带 `if: ${{ always() }}`，否则任务失败时反而收不到通知。

### 4.2 清单明细

先按状态或原因**分组**（组头 + 计数），再树形列出条目：

```
📋 处理结果 · 3
📁 onedrive:media
  ├─ <code>电影/A.mkv</code> · 3.1 GiB
  └─ <code>电影/B.mkv</code> · 800 MiB

📁 onedrive:backup
  └─ <code>backup.tar.gz</code> · 1.150 GiB
```

要点：

- 流水类清单每组建议上限 8 条，超出折叠为「还有 N 条…」；结构性清单不折叠（3.6 节）。
- 组内还有附属明细时降为二层列表（`│ ` 前缀 + 缩进 2 格的 `├─/└─`）：子行前缀必须与
  条目前缀**等宽**（`tree_sub` ≡ `tree_conn`，各 5 字符），否则子行正文比条目正文右移
  一格；子行只补一句话，不搬日志（3.6 节）：

  ```
  📁 onedrive:backup
    ├─ <code>aliyundriveCrypt/backup</code> · 源端 36.065 GiB / 1415 文件 · +7.268 GiB / +2 文件
    │  差异构成：新增 1 · 同名更新 1
    └─ <code>aliyundriveCrypt/media</code> · 无变动
  ```

- 失败清单则**不挂子行**：原因写进条目行的元数据，一句人话说完。

  ```
  ❌ 无法同步文件 · 2
    ├─ <code>media/大文件A.mkv</code> · 超过 45 GiB，需分割后重传
    └─ <code>media/fSWP4H4.jpg</code> · 目标目录不可写（存储端本轮整体故障，未试写；无目录可换）
  ```

- **空清单整段跳过**，不要渲染成 `✅ 已处理 · 0`——图标与计数自相矛盾。零计数的分节
  同理，用 `if [ "$n" -gt 0 ]` 包起来。

### 4.3 复制即用命令块

给人**可复制执行的命令**，而不是数据文件路径（marker / JSON 是人读不懂的落盘载体）。
固定形态是「分节 + 描述说明段 + 命令块」，多条命令重复这一组：

```
🛠️ 复制即用

▸ 强制同步（全量，含本任务）
<pre>gh workflow run openlist.yml -f run_mode=同步 -f force_sync=true</pre>

▸ 还原 3 个非原名文件
<pre>gh workflow run openlist.yml \
  -f run_mode='⚠️ 还原 · 修复文件还原为原路径' \
  -f restore_task=media</pre>
```

参数值要按实际匹配逻辑核实（例如 `restore_task` 按 marker 文件名首个 `_` 前缀匹配，
填完整任务名反而匹配不到）。多行命令用 `\` 续行，整块可直接复制。

### 4.4 失败与异常

- 中文阶段或原因写清楚；原始异常串用 `<code>`；多行日志用 `<pre>`（尾部 1200 字节）。
- 英文 token 与错误码建议中文化：`退出码 45` 而不是 `exit=45`。
- 建议给出下一步动作（复制即用命令，或「见运行日志」）。

```
❌ 下载失败
━━━━━━━━━━━━━━━━━━
文件：<code>video_a.mp4</code>
耗时：12.34 秒

📦 大小
源端：1.150 GiB · 已传：300 MiB

📄 rclone stderr
<pre>ERROR : Failed to copy: connection reset</pre>

请检查源端可用性后重跑本任务。

⏱ 已运行 5 分钟 · 🔗 运行日志
```

**异常与信号兜底分支**是最容易写坏的一块。形态可以极简（标题 + 原因 + 收尾区）：

```
❌ 泰尔三网测速异常退出 · 环境准备失败
━━━━━━━━━━━━━━━━━━
原因：<code>TUN 启动超时：mihomo 未在 30 秒内就绪</code>

⏱ 已运行 1 分钟 · 🔗 运行日志
```

要点：

- 兜底分支**必须留痕**。python 侧统一走 `notify_best_effort(stage, msg)`（内部取返回值
  并记日志）；直接 `send_telegram(...)` 后 `except: pass` 会同时吞掉异常和返回值，
  限流与 400 时完全没有痕迹。
- 发送前先恢复环境（例如先撤 TUN 再发），否则连 API 都送不出去。

### 4.5 凭据与入口通知

按套分节（SSH / RDP / 出口网络），每套内的取值行**整节同为 `标签：<code>值</code>`**
（1.3 节的取值行口径）：出口网络的 IP / ISP / ASN / 位置都是同一次查询的机器返回值，
一律等宽；有效期与共用说明是自然语言，走说明段并保持裸文本。

分节 emoji 不要与标题 emoji 重复（标题已是 🖥️，分节就用 🔐 / 🌐）。完整示例见 2.4 节。

### 4.6 进度面板（原地刷新）

- 标题：刷新态 `🔄 同步进度`；终态按**严重度从高到低**判定——`⛔ 同步中断`（还有
  待处理/进行中，或一个任务都没注册）> `⚠️ 同步完成`（有失败）> `✅ 同步全部完成`
  （无失败，若有文件经修复落盘则在副标题说明）。
  中断必须排在失败之前：中断时伴生的失败只是「没跑完」的副产物，报成「同步完成（有
  失败）」会让人误以为整轮跑完了。
- 五组任务列表（进行中 / 待处理 / 已完成 / 已跳过 / 失败）**全量展示不折叠**——面板
  要一眼看全，折叠掉就等于把「哪些任务没跑完」藏起来。
- 阶段行与批次历史行**整行用 `<code>` 包裹**：计数列在各行间竖向对齐，代价是行宽变长
  （手机上可能折行）。这是面板特有的取舍，其它通知不要这样用，行内机器值仍按 3.3 节
  局部等宽。
- 时长只从收尾区出。

```
⛔ 同步中断
━━━━━━━━━━━━━━━━━━
状态：待处理 4 · 进行中未执行完 2 · 失败 1
📊 总 12 · 待处理 4 · 进行中 2 · 完成 5 · 跳过 0 · 失败 1

🔄 进行中 · 2
  ├─ <code>onedrive:media/电影</code> · 3.1 GiB / 12 文件
  └─ <code>onedrive:media/剧集</code> · 800 MiB / 5 文件

run 已结束，以上任务本轮未执行完

⏳ 待处理 · 4
  └─ <code>onedrive:backup</code> · 1.2 TiB / 3200 文件

❌ 失败 · 1
  └─ <code>onedrive:music</code> · 源端读取被拒

⏱ 已运行 45 分钟 · 🔗 运行日志
```

面板是**唯一需要 message_id 的场景**（原地刷新 = 删旧 + 发新），因此也是唯一允许绕过
发送层直连 API 的地方；并发刷新要用锁串行化，否则会产生孤儿面板消息。

### 4.7 告警通知

形态固定为「对象（机器值）+ 结论 / 原因（裸文本 kv）+ 原始输出（`<pre>` 分节）」，
示例见 2.5 节。要点：

- 对象是包名、标签这类机器返回值 → `<code>`；结论与原因是人写的 → 裸文本。
- 分节后跟 `<pre>` 时**不带** ` · N`（计数只用于条目列表）。
- `<pre>` 是正文最后一块，其后只跟收尾区。

### 4.8 带动作行的通知

正文与动作行（超链接）之间要补一个空行，且**先判断正文是否已有尾换行**，避免产出双
空行：

```
⏳ 起播等待 · 4
  ├─ 你 → Cloudflare → Emby（预估值）：27 毫秒
  └─ 你 → OneDrive 拉流缓冲 · 这段服务器测不到

▶ 打开直链

⏱ 已运行 38 分钟 · 🔗 运行日志
```

## 5. 表达约定

### 5.1 时长

全库统一五层，按量级选：

| # | 形态 | 适用 | 示例 |
|---|---|---|---|
| 1 | `X 小时 Y 分`（分钟**不补零**） | ≥ 1 小时 | `2 小时 8 分`、`1 小时 0 分` |
| 2 | `X 分钟` | ≥ 1 分钟 | `20 分钟`、`45 分钟` |
| 3 | `X.XX 秒`（**两位小数**） | ≥ 1 秒 | `12.34 秒`、`59.00 秒` |
| 4 | `X 毫秒`（整数） | < 1 秒 | `27 毫秒`、`340 毫秒` |
| 5 | `⏱mm:ss`（定宽补零） | 进度面板批次行 | `⏱01:15` |

- 第 1–4 层由三套真源的收尾区实现与各处耗时复用，三者逐字一致；
- 第 3 层的两位小数是**固定精度**（整数秒写作 `12.00 秒`）：精度一致才好纵向比较；
- 第 4 层是子秒专用形态——不足 1 秒若硬走第 3 层会退化成 `0.00 秒`，所以单列一层；
- 第 5 层是**面板列字段**（为了计数列竖向对齐），与第 1–4 层不是一套体系；
- 修饰语前置、值里不重复标签语义：`约 15 分钟`（不是「预计…约 15 分钟后执行」）、
  `3 小时内`、`3 小时前`、`直链剩余 40 分钟`。
- 例外：测速节点指标串（`↑42兆 ↓58兆 35ms`）里的延迟用紧凑 `NNms`——它是指标字段，
  要和 `↑` / `↓` 等宽并排，不走第 4 层的「毫秒」写法。

### 5.2 大小

1024 进制 + 三位小数 + IEC 单位：`1.150 GiB`、`800 MiB`、`12.00 KiB`。
不要用 `du -h` 的 `1G` 口径，也不要输出裸字节（`1234567890 字节`）。

**bash 侧只有一份实现**：通知真源 `tg_notify.sh` 的 `format_bytes`。凡是 source 了
真源的通知点直接用它——openlist 域经 `load_all.sh` 注入，tg-channel 各脚本与 workflow
内联各自 source 真源。此前 openlist / tg-channel / workflow 内联各有一份同义实现，
改口径要四处同步极易漏改，已收敛。

python 侧拿不到 bash 函数，仍有两处同义实现（`add_uploaded_video.py` 与
`sync_to_tg.sh` 内嵌段），改口径时这两处要跟着改。

### 5.3 日期与相对时间

`YYYY-MM-DD HH:MM UTC` + ` · N 小时前`（解析失败保留原值）：

```
时间：2026-09-07 11:34 UTC · 3 小时前
```

不要直出 ISO 时间戳（`2026-09-05T11:34:19Z`）。

### 5.4 计数与量化

- 分节计数：`{emoji} 分节 · N`。
- 影响写进 kv 的计数与量化：失败 3 个 / 减少 100 GiB / 跳过 12 条。
- 错误码中文化：`退出码 45` 而不是 `exit=45`。
- 面板批次行定宽：`✅00 🔧00 ❗33 ⏭️22 ♻️22 ⏱01:15 ⬆️4.79G`——五个计数补零，
  上传量取 GiB 两位小数，最近 6 条滚动。

### 5.5 状态图标语义

`✅` 成功 · `⚠️` 部分失败/警告 · `❌` 失败 · `⏭️` 跳过 · `🔄` 进行中 ·
`⏳` 待处理 · `⛔` 中断 · `🚨` 危险警告 · `🆘` 灾难恢复 · `📍` 进度面板当前阶段

建议图标与结论一致，不要自造 `⭐` / `🥇` 之类前缀。同一条通知里避免两个相同 emoji
承担不同角色（如两个 `📍`）。

### 5.6 常见偏差与改进建议

| 偏差 | 为什么会这样 | 建议改成 | 渲染后 |
|---|---|---|---|
| 手拼 HTML（`msg+="<code>…"`） | pwsh 无助手；bash/python 已全部走助手 | 用 6.3 节的助手（pwsh 按第 3 章形态手拼、值经 `Esc-Html`） | `tg_entry "video.mp4" "1.7 GB"` → `<code>video.mp4</code> · 1.7 GB` |
| 分节后跟列表却没计数 | 忘了拼 | 带 ` · N` | `❌ 失败清单 · 3` |
| 条目用 `• ` 平铺 | 沿用了平铺写法 | 改 `├─/└─` 树形 | `  ├─ <code>video_a.mp4</code>` |
| 长列表全量穷举（流水类） | 怕漏信息 | 分组 + 每组 8 条 + 折叠行；结构性清单不折叠 | `  └─ 还有 35 条…` |
| 英文紧凑时长（`5h 57m`） | 脚本内部格式直接输出 | 中文分层（5.1 节） | `⏱ 已运行 5 小时 57 分` |
| 高精度浮点（`2.16068914 秒`） | 原始值直出 | 两位小数 | `起播 2.16 秒` |
| ISO 时间戳直出 | 原始值直出 | UTC + 相对时间 | `2026-09-05 11:34 UTC · 15 小时前` |
| 半角冒号 kv（`状态: 成功`） | 手误 | 全角冒号 | `状态：成功` |
| 手拼收尾行 | 不知道有助手 | 一律 `tg_add_footer` / `Get-TgFooter` / `tg_footer_line` | `⏱ 已运行 22 分钟 · 🔗 运行日志` |
| 已引入发送层仍 curl 直发 | 想要 message_id 等 | 除进度面板外一律走发送层 | `send_tg "$msg"` |
| 失败原因写内部机制（熔断 / 探测 / 哈希目录） | 直接透出实现层的判据变量 | 翻成人话（1.5 节），细节留日志 | `目标目录不可写（存储端本轮整体故障，未试写；无目录可换）` |
| 把运行日志搬进通知当条目子行 | 想省一次点链接 | 子行只补一句话，过程走运行日志链接 | `  └─ <code>f.mp4</code> · 目标目录不可写（…）` |
| 子行前缀比条目前缀宽一格（6 vs 5 字符） | `tree_sub` 比 `tree_conn` 多写一个空格 | 两者定宽必须相等（4.2 节） | `  │  差异构成：…` 与 `  ├─ <code>dst</code>` 正文同列 |

## 6. 三套实现与接线

### 6.1 选哪套

| 场景 | 用哪套 | 有什么 / 没什么 |
|---|---|---|
| Linux / macOS runner 的 bash step | `.github/scripts/telegram/tg_notify.sh` | 助手最全：排版、条目、树形、折叠、收尾、发送都有 |
| Windows runner（pwsh） | `.github/scripts/telegram/tg_notify.ps1` | **只有** `Esc-Html` / `Format-TgDuration` / `Get-TgFooter` / `Send-TgMessage` / `$TG_SEP`——没有 kv 与条目助手，全部手拼，也没有分片发送 |
| python 脚本 | `.github/scripts/proxy-speedtest/speedtest_common.py` | 有条目与收尾的镜像函数（返回字符串，需自己 `join`），**没有** `tg_add_*` 变量累积机制 |
| bash 里内嵌的 python 段 | 无法 import 共享层 | 必须在本文件内同义实现用到的助手 |

### 6.2 接线

每个发通知的 step 都需要：

```yaml
      - name: "Notify: xxx 结果"
        if: ${{ always() }}
        env:
          TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
          TG_RUN_URL: https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}
          TG_RUN_STARTED_AT: ${{ github.run_started_at }}
```

- 凭据校验在**调用方**，且放在引入真源**之前**：`if [ -z "$TELEGRAM_BOT_TOKEN" ] …exit 0`。
  真源本身不校验。
- bash 真源兼容历史变量名 `TG_BOT_TOKEN` / `TG_CHAT_ID`；**pwsh 侧没有这层回退**，
  必须注入 `TELEGRAM_*`。
- python 侧凭据从传入的 `env` 读，但 `TG_RUN_URL` / `TG_RUN_STARTED_AT` 只读
  `os.environ`，只给 dict 不够。
- pwsh 的 step 要 `shell: pwsh`；引入真源后建议加 `Get-Command Send-TgMessage` 自检——
  调用未定义函数是终止错误，step 带 `continue-on-error` 时会表现为通知静默消失。

### 6.3 助手速查

| 用途 | bash 真源 | pwsh | python |
|---|---|---|---|
| 标题 / 分节 | `tg_add_title` / `tg_add_section` | `$TG_SEP` 手拼 | 手拼 + `TG_SEP` |
| kv / 机器值 | `tg_add_kv` / `tg_add_path` | 手拼 | 手拼 |
| 条目（单主体） | `tg_entry` / `tg_add_entry` | — | `tg_entry(subject, *meta)` |
| 条目（文字主体） | `tg_entry_text` / `tg_add_entry_text` | — | `tg_entry(..., code=False)` |
| 条目（双机器值 `→`） | `tg_entry_pair` / `tg_add_entry_pair` | — | `tg_entry_pair(a, b, *meta)` |
| 条目（双机器值 `·`） | `tg_entry_codes` / `tg_add_entry_codes` | — | `tg_entry_codes(a, b, *meta)` |
| 多行块 | `tg_add_pre` | — | `tg_pre_block(text)` |
| 说明段 | `tg_add_note` | 手拼 | 手拼 |
| 树形 / 折叠 | `tree_conn` `tree_sub` `tree_lines` `tree_code_fold`（裸文本）/ `tree_fold`（已构建条目流） | 手拼 | 手拼 |
| 大小格式化 | `format_bytes` | 手算 | 手算（python 侧同义实现） |
| 转义 | `escape_html` | `Esc-Html` | `html.escape` |
| 收尾 | `tg_add_footer` | `Get-TgFooter` | `tg_footer_line` / `tg_format_elapsed` |
| 发送 | `send_tg` / `send_tg_chunked` | `Send-TgMessage` | `send_telegram` / `send_telegram_chunked` |
| 原始追加（**不转义**） | `tg_append` | — | — |

`tg_add_*` 的第一参是**变量名**不是值（内部按名字追加）。`tg_add_entry` 收的是**裸
主体**，内部才包 `<code>` 并转义——预先包好再传会二次转义。

### 6.4 内嵌 python 段

bash 里内嵌的 python 段（`python3 - <<'PY'`）无法 import 共享层，用到的助手必须在本
文件内同义实现，且与共享层逐字一致。**新增助手时别忘了同步补进内嵌段**——否则会出现
`NameError` → python 非零退出 → 脚本提前退出 → 连整轮汇总通知一起丢。这类问题代码
审查很容易漏（函数名看着就像内置的），改完务必实跑一次。

## 7. 发送层要求

> 这一章是**硬约束**。

- **一律 HTML parse_mode**，动态内容**必须**转义（`escape_html` / `Esc-Html` /
  `html.escape`，或经 `tg_*` 助手自动转义）。没有「值是脚本自造、字符集受限」的豁免。
- **HTML 解析失败（400 can't parse entities）不重发**，直接报错暴露并带上响应体前
  200 字符：消息本来就没发出去，退化成纯文本只会把 bug 藏起来。
- **429 限流按 `retry_after` 等待重试（最多 5 次尝试）**；长消息按 4000 字符分片
  （断在换行处，不切 UTF-8 多字节）。
- 发送失败**必须**在 stderr / 日志输出原因（含响应体前 200 字符），由调用方决定
  `|| true` 还是失败；**不要 `>/dev/null 2>&1` 吞掉**。python 侧 `send_telegram` 返回
  字典（失败带 `reason`），调用方**必须**把原因记进日志。
- **已引入发送层的通知点不得 curl 直发**。唯一例外是需要 message_id 的进度面板原地
  维护（4.6 节）。
- 媒体上传（`sendDocument` / `sendVideo`）不走 sendMessage 发送层（固有例外），但
  caption **必须**转义、429 重试与发送层同口径（最多 5 次）。

已知差异（不是规范，是现状，修完可删）：

- pwsh 侧无分片实现，超长消息会被 Telegram 直接拒。
- python 侧 429 耗尽路径是抛异常而非返回字典。
- bash 侧 `TG_RUN_STARTED_AT` 有值但解析失败时，不再回落开机时刻，时长直接消失。

## 8. 验证与交付

### 8.1 渲染预览

改动版式后，用真源助手构造数据渲染一遍再交付：

```bash
source .github/scripts/telegram/tg_notify.sh
msg=""; tg_add_title msg "⚠️ 示例"; tg_add_section msg "❌ 清单 · 2"

```

### 8.2 回归套件

改到 openlist 域的脚本时跑回归（`.github/scripts/openlist/tests/` 下的套件）：

```bash
for t in test_*.sh; do bash "$t" </dev/null > "/tmp/x_${t%.sh}.log" 2>&1; echo "$t EXIT=$?"; done
grep "command not found" /tmp/x_*.log
```

- 必须重定向 stdin，否则个别套件会卡在读 stdin。
- **套件 PASS 不等于通过**：跑完必须 grep `command not found`，**必须为空**——函数没
  被引进来时测试可能照样 PASS。
- 具体基线（各套件的预期结果与已知环境失败）见
  `skills/telegram-notify-audit/references/audit-checklist.md`，那边会随实现更新，
  这份文档不再复制一份数字。
- 几个依赖本机环境的套件：需要 docker 或真实服务的、用到 GNU `date -d` 的（macOS 的
  BSD `date` 没有 `-d`）、以及时序敏感的。跑出来与基线不符时先单独复跑确认，别急着
  改代码。

## 9. 术语

- **面板**：需要 message_id 的原地刷新消息（openlist 进度面板）。
- **结构性清单**：读者要逐条核对、折叠掉会造成误判的清单（与流水类相对）。
- **硬约束**：不遵守会造成通知丢失或误判失败的规则（第 7 章、3.9 节、第 8 章）。
